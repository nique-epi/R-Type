This page is the specification of the protocol the client and the server speak: the format of every datagram and message, the values each field takes, the order of the exchanges from the connection to the end of a game and the departure or the crash of a peer, and what each side does with what it cannot accept. A developer who follows it can write a client for this server, or a server for this client, without reading the code.

## Status of this document

- This is version 16 of the protocol. It is the only version the code speaks. - The words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. A MUST is a rule every implementation follows to interoperate; a SHOULD names a behavior the code of this repository has and another implementation can drop without breaking the exchange.
- Everything on this page is checked against the code of `src/network`, `src/server` and `src/client`. [Implementation status](#implementation-status) lists the rules the programs do not apply yet, so a rule never reads as working when it does not.
- Numbers are decimal unless written `0x`. A size is in bytes.

## Overview

The client and the server exchange datagrams over UDP. A client asks to join, the server admits it to a waiting room, starts the game once every connected player is ready, then sends the state of the world about 20 times per second while the client sends the keys held 60 times per second. The sections below follow that order: [Transport](#transport) and [Encoding](#encoding) fix the bytes, [Datagram](#datagram) the header and the checks, [Messages](#messages) every message, [A session](#a-session) the exchanges and their timing, [Errors](#errors) and [Losses](#losses) what goes wrong.

## Transport

- Every message of the game travels over UDP. The one exception is the content pack of a server, a file a client that lacks it downloads over HTTP, on TCP, once it is accepted (see [Content pack](#content-pack)).
- The server listens on one port. The client sends from any port, and the server answers to the address and port the datagram came from.
- A datagram carries at most 1200 bytes of UDP payload. Every IPv6 link carries packets of 1280 bytes or more (RFC 8200, section 5); minus the 40-byte IPv6 header and the 8-byte UDP header, that leaves 1232 bytes, so 1200 keeps room for 32 bytes of IPv6 extension headers. QUIC relies on the same figure and expects it to pass on all IPv6 paths and on modern IPv4 paths (RFC 9000, section 14). A path with a smaller MTU, such as some VPNs and tunnels, may still fragment or drop a datagram; the protocol does not detect it.
- A datagram is read on its own: no message is split across two datagrams.

## Encoding

Each field is written and read one at a time, never copied from memory as a struct, so neither padding nor the byte order of the machine reaches the wire. Integers are big-endian, the order the IP and UDP headers use for their own fields, so a number reads in a capture the way it is written: `protocolId` shows as `52 54 59 50`.

| Type | Size | Encoding |
|---|---|---|
| `u8`, `u16`, `u32`, `u64` | 1, 2, 4, 8 bytes | unsigned, big-endian (most significant byte first) |
| `bool` | 1 byte | 0 is false, 1 is true, any other value is invalid |
| `position` | 4 bytes | x then y, each a signed 16-bit integer (two's complement, big-endian) counting eighths of a logical unit |
| `string` | 1 + n bytes | length `u8`, then n bytes of UTF-8, no terminator |
| enumeration | 1 byte | `u8`; a value not listed on this page is invalid |

### Positions

A position is in logical units, in the frame described in [Architecture](/R-Type/architecture/#coordinate-system). Each coordinate is rounded to the nearest eighth of a unit: 8 on the wire is 1 unit, -8 is -1 unit. The range is -4096 to 4095.875 units and the rounding error is at most 0.0625 unit; every multiple of an eighth survives the round trip through a `float` exactly.

- The range holds the playfield plus one playfield size beyond each edge as long as `PLAYFIELD_WIDTH` and `PLAYFIELD_HEIGHT` stay at or below 2047 units. The code must check this at compile time, so enlarging the playfield breaks the build instead of sending positions to the opposite edge.
- The server must destroy an entity before it leaves the range: a coordinate outside it is a bug. As a last resort, so that a coordinate never wraps to the opposite edge, the encoder clamps it to the nearest end of the range; this hides nothing from the server, which must still not let an entity get there.

### Packing

Every field takes the smallest whole number of bytes its values need, and flags that travel together share one byte, one bit each; nothing is written bit by bit across bytes, and the server compresses the result (see [Compression](#compression)). Since the first version, a coordinate is an `i16` instead of a 4-byte float, the five actions of a `PlayerInput` are bits 0 to 4 of `actions`, and the six flags of a pilot are bits 0 to 5 of `motion`.

`PackingMeasurement` (`tests/network/Protocol/`) encodes a typical state twice: once with `WorldStateCodec`, once with a writer of the tests that puts each coordinate in a binary32 float and each bit of `motion` or `actions` in a byte of its own. The state is `LARGE_WORLD_STATE_BODY`, a `WorldState` the server sent during a real game of four players and 22 entities; the input holds up and shoot and repeats five inputs the server has not confirmed yet, as a client does between two world states.

| Payload | Packed | Unpacked | Saved |
|---|---|---|---|
| Typical world state | 268 bytes (6 + 16 per player + 9 per entity) | 376 bytes (6 + 21 per player + 13 per entity) | 108 bytes, 28.7 % |
| `PlayerInput` with 5 repeats | 15 bytes | 39 bytes | 24 bytes, 61.5 % |

At 20 states and 60 inputs per second, that is 2160 bytes per second less to each client and 1440 less from it, before compression. The unpacked form is never sent: it exists only to give the figure. The test prints both sizes:

```bash
ctest --test-dir build -R PackingMeasurement -V
```

What each field could still lose:

| Field | On the wire | Values | Why it stays |
|---|---|---|---|
| coordinate | `i16` | eighths, -4096 to 4095.875 units | already 2 bytes; the range holds the playfield and one playfield beyond each edge |
| entity id, `shipEntityId` | `u32` | handed out once by `NetworkIdAllocator`, never reused | 16 bits would wrap after 65535 entities, within a long game, and need ids recycled |
| `score` | `u32` | can pass 65535 | |
| `lives`, `playerNumber`, `entityType` | `u8` | 0 to 3, 1 to 4, the [entity types](#entity-types) | one byte is the least without writing bit by bit |
| `invulnerable` | `bool` | one bit | could take bit 6 of `motion`: 1 byte per player |
| `acknowledgedInput` | `u32` | grows by 60 per second | 16 bits would wrap after 18 minutes and need serial number comparison: 2 bytes per player |

Both changes together save 12 bytes on the 268 of the typical state, 4.5 %, before compression; they are left out, since each needs a new `version` and a new dictionary.

## Datagram

A datagram is a 22-byte header followed by one or more messages. The header, byte by byte; every field is used in version 16.

| Offset | Size | Field | In version 16 |
|---|---|---|---|
| 0 | 4 | `protocolId` | `0x52545950`, `RTYP` in ASCII |
| 4 | 1 | `version` | 16 |
| 5 | 1 | `flags` | `ACKNOWLEDGES` 0x01, `GUARANTEED` 0x02, `COMPRESSED` 0x04, every other bit 0 |
| 6 | 8 | `sessionToken` | 0 until the connection is accepted, then the token given by the server |
| 14 | 2 | `sequence` | number of the datagram for its sender |
| 16 | 2 | `acknowledgedSequence` | the newest sequence accepted from the peer, when `ACKNOWLEDGES` is set |
| 18 | 4 | `acknowledgementBits` | bit n set: the datagram n + 1 before `acknowledgedSequence` was accepted too |

Each message is a type (`u8`), the size of its payload in bytes (`u16`, the 3 bytes of type and size excluded), then the payload. A receiver accepts several messages in one datagram and reads them in order; the server groups in one datagram the guaranteed messages it sends again (see [Guaranteed messages](#ordered-messages)).

- `protocolId` and `version` stay at offsets 0 and 4 in every future version, so a receiver tells which version sent a datagram from its first 5 bytes.
- `sessionToken` is drawn at random by the server when it accepts a connection, never 0. The server writes it in every datagram it sends to that client, and the client copies it into every datagram it sends afterward. Within a session, each side drops and counts a datagram that carries another token, so nobody can steer a ship, or feed a client false states, by forging an address. A `ConnectionRequest` carries 0, since the client has no token yet: it never keeps a session alive, and it only gets a player slot with a valid cookie (see [Connection](#connection)).
- `sequence` counts the datagrams a side sends to the other: one counter per peer, starting at 0 with the first datagram to that peer, growing by 1 and wrapping from 65535 to 0. Within a session, a receiver drops a datagram that is not newer than the newest one it has accepted from that peer, so a late or duplicated datagram never undoes a newer one. Newer means ahead by 1 to 32767 modulo 65536 (serial number arithmetic, RFC 1982), so the comparison survives the wrap. Datagrams sent outside a session (`ConnectionChallenge`, `ConnectionRefused`, `ServerInformationRequest`, `ServerInformation`, `MasterProbe`) carry 0 and are not compared.
- `flags`: `ACKNOWLEDGES` (0x01) says that `acknowledgedSequence` and `acknowledgementBits` name the datagrams the sender accepted from its peer within the session; a side sets it from the first datagram it accepted. `GUARANTEED` (0x02) says that the datagram holds guaranteed messages (see [Guaranteed messages](#ordered-messages)). `COMPRESSED` (0x04) says that the body is a zstd frame (see [Compression](#compression)). The other five bits are 0.
- `acknowledgedSequence` is the newest sequence the sender accepted from its peer, and bit n of `acknowledgementBits` (bit 0 the least significant) is set when the datagram n + 1 before it was accepted too, so a header names the 33 newest datagrams. A datagram dropped for its sequence, late or duplicated, is never acknowledged.

Version 1 reserved these fields, so version 2 guarantees messages without moving a field of any datagram. The header costs 17 bytes per datagram more than a 5-byte header: about 11 kbit/s per client at 60 inputs and 20 states per second.

Alternative considered: a 5-byte header (`protocolId`, `version`) and a later version that adds the rest. It is smaller, but the token checked from the first version needs its 8 bytes anyway, and adding the sequence and the acknowledgements in the middle of the project changes the layout of every datagram (they live in `Sessions` and `Reliability`, see [Project layout](/R-Type/project-layout/#network)).

### Receiving a datagram

A received datagram goes through these checks in order. No buffer is sized from a field before that field has been checked against the bytes actually received, and every rejection is logged with its sender, at a bounded rate.

| Check | If it fails |
|---|---|
| The datagram holds 25 to 1200 bytes | dropped |
| `protocolId` is `RTYP` | dropped |
| `version` is 13 | dropped; the server answers an unknown sender with `ConnectionRefused` (`IncompatibleVersion`) if the datagram holds at least 26 bytes |
| `COMPRESSED` is set | the server drops the datagram; the client decodes the body and clears the flag, or drops the datagram when it cannot (see [Compression](#compression)) |
| `flags` has no bit but `ACKNOWLEDGES` and `GUARANTEED`, once `COMPRESSED` is cleared | dropped |
| The message sizes add up exactly to the end of the datagram | dropped |
| The sender is known, or the datagram holds a `ConnectionRequest`, a `ServerInformationRequest` or a `MasterProbe` | dropped |
| Within a session, `sessionToken` is the token of the session (a `ConnectionRequest`, a `ServerInformationRequest` or a `MasterProbe` may carry 0) | dropped and counted |
| Within a session, `sequence` is newer than the newest one accepted from that peer | dropped |
| The message type is listed below | that message is skipped, the next one is read |
| The payload has the size its type requires and every value is in range | that message is dropped |

The token is checked before the sequence, so a forged datagram never moves the counter. The server reads the acknowledgements of a datagram only once it passed every check above, so a forged or replayed datagram acknowledges nothing. A datagram dropped for its sequence is not heard from the peer: it does not restart the silence count of [A session](#a-session).

The server measures the loss rate of each player from the gaps in `sequence`. Each datagram it accepts counts as received, and the sequences it skips over count as lost; every 100 datagrams counted, received or lost, it takes the share lost as the loss rate of that player and starts counting again. A datagram that arrives late and is dropped stays counted as lost. Nothing is added to the wire. The server never sends a sender that did not prove its address more bytes than the datagram it answers, so a forged source address cannot turn it into an amplifier: a `ConnectionRequest` holds at least 38 bytes, and every answer to a request without a valid cookie at most 33 (`ConnectionChallenge`). Only a request with a valid cookie gets a `ConnectionAccepted`, which is larger, 64 bytes (see [Connection](#connection)). A `ServerInformationRequest` is padded to 106 bytes, and its answer holds at most 106 (see [Server information](#server-information)); a `MasterProbe` gets no answer (see [Probe of the master](#probe-of-the-master)). A client that receives a datagram of another version decodes nothing in it. While it connects to the server that sent it, it ends the attempt and reports both version numbers to the player: its own, and the one at offset 4; within a session it drops it, so a datagram forged with the address of the server cannot end the session.

### Payload rules

A message is accepted only when its payload has exactly the size its fields add up to, with no byte left over, and every value is in range. These rules complete the tables above; a message that breaks one is dropped (see [Errors](#errors)).

| Message | Rule |
|---|---|
| `ConnectionRequest` | the nickname follows the rules of [Connection](#connection): 1 to 16 bytes of valid UTF-8, no control character; `kind` is 1 to 3; `number` is 1 to 65535 with `ExistingGame`, and 0 with `AnyGame` and `NewGame`; the rules follow `number` with `NewGame` and with no other kind; their `difficulty` follows the rules of a nickname. Any `lives` byte is read: the supervisor refuses those it does not accept (see [Supervisor](#supervisor)) |
| `ConnectionAccepted` | `playerNumber` is 1 to 4; `size` is 8388608 at most; the payload is 39 bytes |
| `LobbyState` | at most 4 players, each `playerNumber` 1 to 4 and listed once, each nickname valid as above |
| `GameEnded` | `outcome` is 1 or 2; at most 4 players, each `playerNumber` 1 to 4 and listed once |
| `WorldState` | at most 4 players, each `playerNumber` 1 to 4 and listed once; `motion` follows [World state](#world-state) |
| `EntitySpawned` | `entityId` is not 0, `entityType` is not 0, `owner` is 0 to 4 |
| `EntityDestroyed`, `PlayerLeft`, `ConnectionRefused` | `reason` is in the table of its message; `PlayerLeft` names a `playerNumber` of 1 to 4 |
| `GameEvent` | `kind` is in the table of [Game events](#game-events), and `playerNumber` and `entityId` are 0 or a valid value as that table says |
| `RoundTrips` | at most 4 players, each `playerNumber` 1 to 4 and listed once |
| `EnemyAction` | `entityId` is not 0, `phase` is in the table of its message; `attack` is any `u8`, since the sheet of the enemy gives it its meaning |
| `BossStatus` | the payload is 9 bytes; `stage` is in the table of its message; with `Arriving`, `bossEntityId`, `health` and `fullHealth` are 0; with any other stage, `bossEntityId` and `fullHealth` are not 0, `health` is at most `fullHealth`, and `health` is 0 exactly with `Defeated` |
| `Heartbeat` | `echoes` and `ticks` are 0 or 1; when `echoes` is 0, `echo.sentAt` and `echo.heldFor` are 0; when `ticks` is 0, `tick` is 0 |
| `Disconnection`, `GameStarted` | the payload is empty |
| `LeaderboardRequest` | `playerCount` is 1 to 4, or 0 (`ALL_PLAYER_COUNTS`) for every number of players; `difficulty` follows the rules of a nickname, 1 to 16 bytes of valid UTF-8, no control character, or is empty (`ALL_DIFFICULTIES`) for every difficulty |
| `LeaderboardAnswer` | as `LeaderboardRequest` for its first two fields; at most 10 rows; each `rank` is at least 1 and each nickname is valid |
| `ServerInformationRequest` | the payload is 81 bytes: `sentAt`, then 77 bytes of 0; a shorter or longer one, or a byte of `padding` other than 0, is invalid |
| `ChatLine`, `PlayerChatLine` | `text` is 1 to 127 bytes of valid UTF-8, no control character; `PlayerChatLine` names a `playerNumber` of 1 to 4 |
| `ShipLookChoice`, `PlayerLooks` | each look byte is 0 or the number of an item of its slot: `head` 0 to 8, `eyes` 0 or 9, `face` 0 or 10; `PlayerLooks` has at most 4 players, each `playerNumber` 1 to 4 and listed once |
| `LookItemWon` | `item` is 1 to 10 |
| `EffectPlayed` | `entityId` is not 0; `effect` is a name of the content, 1 to 24 bytes of `a` to `z`, digits and `_`; whether the sheet of the body names it is for the receiver to look up |
| `LevelStatus` | `biome` is empty or a biome name: 1 to 24 bytes among `a` to `z`, `0` to `9` and `_`; `scrollPosition` and `scrollSpeed` are finite and not negative |
| `ServerInformation` | `gameVersion` and `name` are 1 to 32 bytes of valid UTF-8, no control character; `playerCount` is at most 4 times `gameCount`, and `playerCount` plus `freeSeatCount` too |
| `ExpulsionOrder` | the nickname follows the rules of a nickname: 1 to 16 bytes of valid UTF-8, no control character |
| `Expulsion` | `reason` is in the table of its message; the payload is 1 byte |
| `GameStatus` | `state` is in the table of its message; at most 4 nicknames, each following the rules of a nickname; the measures byte sets no bit above bit 2, and the payload ends after the last measure it announces |
| `MasterProbe` | the payload is 16 bytes: `secret`, then `token`; a shorter or longer one is invalid |

A `LobbyState` or a `GameEnded` with no player is well formed; a `WorldState` too, while the game has none. A `LeaderboardAnswer` with no row is well formed.

### Leaderboard

A leaderboard belongs to one server, and to one difficulty and one number of players at the start of a game, or to every one of them when the request asks for all (`ALL_DIFFICULTIES`, `ALL_PLAYER_COUNTS`): the leaderboard screen opens on all of them. Each player appears once, with their best score among the games the request reads. A server older than this rule refuses a request for all as a malformed one, and the client then waits as for a server that does not answer. Equal scores share a rank and the next rank skips (1, 1, 3); among them, the earliest game comes first. The player who asks gets their own row whether or not it is among the 10 listed, so it may appear twice. A guest is recognized by nickname, with no proof that it is the same person.

The server reads a request only from a player with a session, in any state of the game: it drops one from any other sender before reading it, so an answer larger than its request never goes to an unverified address. It answers a player at most once per 500 ms and ignores the other requests.

### Chat

A player chats in any state of the game: in the waiting room, during a match and on its end screen. The server reads a `ChatLine` only from a player with a session, and relays each new line to every player of the game at that moment, its writer included, as a `PlayerChatLine` on the ordered channel (see [Ordered messages](#ordered-messages)). The server writes `playerNumber`: a client never names who wrote a line. A player who joins later never gets the lines relayed before.

- **Numbering.** The lines of a player are numbered from 1 within its session, one more for each new line, wrapping from 65535 to 0. A copy keeps the number of its line.
- **Sending again.** The client to server direction has no guaranteed channel, so a client MUST send a line again every 500 ms until it receives the `PlayerChatLine` with its own `playerNumber` and that `lineNumber`, and SHOULD give up after 5 s. It sends one line at a time: the next one waits until the previous came back or was given up.
- **Copies.** The server keeps, for each player, the `lineNumber` of the newest line it relayed. A line whose number is not newer, compared as the `sequence` of a datagram is (RFC 1982: newer means ahead by 1 to 32767), is a copy: the server ignores it.
- **Rate.** The server relays at most one line per player per second. A new line sooner is ignored without being kept, so a later copy of it goes through once the second is over: a fast writer is slowed down, it loses no line. Quake III takes one command a second from each client the same way.
- **Length.** A text holds 1 to 127 bytes, the length at which Source cuts a line of chat; a longer one is refused as [Payload rules](#payload-rules) say.
- **Departure.** What the server keeps of the lines of a player is forgotten when its session closes, so the next player on that seat starts afresh.

Alternative considered: a guaranteed channel from the client to the server. It would spare the number and the copies, but the server would have to acknowledge, which it never does, so it changes both programs for one message; the number of a line costs 2 bytes.

Alternative considered: a bucket of lines, as Source keeps (4 lines at once, then one every 3 s). It lets a player send a burst, but it is a second mechanism next to the interval the leaderboard already uses.

### Ship looks

A player dresses its ship in the hangar with items of a locker of 10: 8 for the head (numbers 1 to 8), the shades for the eyes (9) and the mustache for the face (10). A look is three bytes, one per slot, 0 for a slot that wears nothing. The server shows the look of every player to every player, in the waiting room and in the game.

- **Choosing.** The server reads a `ShipLookChoice` only from a player with a session, and only while the game takes the choices of the waiting room, as it does a `ReadyState`; one sent during a game is ignored. The value is absolute, never a change.
- **Sending again.** The client to server direction has no guaranteed channel, so a client MUST send its look again every 500 ms until a `PlayerLooks` lists its own `playerNumber` with that look, and sends nothing once the game started.
- **Copies.** A look equal to the one the server keeps for the player is a copy: the server answers it to its sender alone, so a client whose confirmation was lost still gets it, and writes to no other player. A changed look goes to every player.
- **Rate.** The server takes at most one `ShipLookChoice` per player every 100 ms (6 ticks). A choice sooner is ignored and not kept, so its next copy goes through.
- **Arrival.** The server sends a `PlayerLooks` to every player each time a player arrives, so a newcomer sees the others and the others see its empty look. A seat freed by a departure forgets its look, so the next player on it wears nothing.
- **Winning.** A look item is an entity whose sheet has the side `look_item`. When a ship touches it, the server records the touch, and at the start of the next tick it gives the item to the lowest `playerNumber` among the pilots who touched it and still fly the ship that touched it, removes it (`EntityDestroyed`, `Removed`) and sends that player alone a `LookItemWon`. An item no such pilot is left for stays. The client keeps the number in its locker.

Alternative considered: a `GameEvent` kind for the item won. It needs no new type, but a decoder refuses a kind it does not know, so an older client would count the whole message malformed, and the numbers of the events are global to a game.

### Server information

Anyone may ask a server what it is, without a session, on the port of its supervisor; a game process answers none: a client measures its ping to the servers of the master this way, since the server map places every server by its ping: one request to each server of this version the master lists, at each reading of the list (every 15 s and on R), while the rest of their information comes from the master. A `ServerInformationRequest` carries `sentAt`, the time it leaves on the clock of its sender, in microseconds modulo 2^32, as a `Heartbeat` does (see [Round trip](#round-trip)), with a session token and a `sequence` of 0. The server keeps nothing and answers with one `ServerInformation`, to the address and port the request came from:

| Field | Holds |
|---|---|
| `sentAt` | the `sentAt` of the request, unchanged |
| `heldFor` | the microseconds from the arrival of the request to the answer |
| `protocolVersion` | the version the server speaks, the one at offset 4 of its header |
| `gameVersion` | the version of the game it runs, such as `0.1.0` |
| `name` | the name players read in the list of servers |
| `playerCount` | the players seated in its games, away ones included, as each game last told its supervisor |
| `gameCount` | the games it may run at once, whatever their state: `MAXIMUM_RUNNING_GAMES` (8) for a supervisor |
| `freeSeatCount` | the empty seats of the games that wait for players or start, plus four for each place no game holds: a game that started gives none |

The asker reads the round trip as the time since the request left, less `heldFor`, both on its own clock, so the time the request waited in the server for its tick is left out; an answer held longer than its trip, or back after more than 20 s, gives none.

- The request is padded with 77 bytes of 0, so its datagram holds 106 bytes, the size of the largest answer, with a name and a game version of 32 bytes. A forged source address never gets more bytes than its forger sent, as QUIC pads its first datagram (RFC 9000, section 8.1). A request of another size is dropped without an answer.
- A datagram gets one answer, to its first `ServerInformationRequest`; one that also holds a `ConnectionRequest` is answered as a connection request only.
- The requests spend the limit of the connection requests of their address and port: one sender places 11 requests of either kind at once, then 4 a second (see [A sender that sends too much](#a-sender-that-sends-too-much)).
- Nothing on this page sends a request again: an asker that gets no answer asks again when it chooses.

### Probe of the master

The master checks that the UDP port of a game server can be reached from outside, without a session and without listening on UDP itself. After each heartbeat it accepts over HTTP, it sends the address and UDP port the server registered with one `MasterProbe`, with a session token and a `sequence` of 0:

| Field | Holds |
|---|---|
| `secret` | the `probeSecret` the server registered with (see [Master](/R-Type/master/#probing-the-game-servers-masterprobemodule)) |
| `token` | a keyed hash of the address, the port and the current 5-second window, which the master recomputes instead of keeping it |

The server answers nothing over UDP. It keeps the token of a probe whose `secret` is its own, and sends it back once, as `probeToken`, in its next heartbeat over HTTP; the master accepts a token in its window and the two after it. A probe whose `secret` is another is dropped, so a forged probe never replaces the token of the master.

- The datagram of a probe is 41 bytes: the header, the prefix of the message and 16 bytes of payload. The master sends it to an address that just sent it a heartbeat over HTTP, a larger message, and never more than one per second to one address and port.
- A probe spends the limit of the requests of its address and port, as a `ConnectionRequest` does (see [A sender that sends too much](#a-sender-that-sends-too-much)); the server reads at most 16 per tick.
- A datagram that also holds a `ConnectionRequest` or a `ServerInformationRequest` is read as that request only, and its probe is ignored.

### Connection

A connection takes two round trips, so that a forged address never gets a player slot. The client sends `ConnectionRequest` with `cookie` 0; the server answers `ConnectionChallenge` with a cookie and keeps nothing. The client sends its request again with that cookie, and only then does the server give a slot, a token and the [content pack](#content-pack) it plays with. The cookie only reaches the real owner of the address, so whoever forges the address cannot send it back. A request with a wrong or expired cookie gets a new challenge; a refusal (`GameFull`, `GameInProgress`, `NicknameTaken`, `IncompatibleVersion`, `GameNotFound`, `ServerFull`, `UnknownDifficulty`, `LivesOutOfRange`) may be sent at once, since it reserves nothing.

How the server computes the cookie is its own business, as long as it keeps nothing per request and nobody can guess it: a keyed hash of the address, the port and the current 10-second window, with a secret drawn when the server starts, accepted during its window and the next one, does both.

A player keeps the number given by `ConnectionAccepted` until it leaves; the number also picks the color of the player, so no color travels. The nickname travels only in `ConnectionRequest` and `LobbyState`, never during a game. Its limit is 16 bytes, not 16 characters: a letter without accent takes 1 byte, an accented letter 2 and some symbols up to 4, so each accent leaves room for one letter less. The text field of the client counts bytes and refuses a character that would not fit whole; the server drops a request whose nickname is empty, longer than 16 bytes, not valid UTF-8 or holds a control character, U+0000 to U+001F or U+007F, so a nickname can never start a line of its own in a log. The server answers a `ConnectionRequest` with a valid cookie from a sender it already accepted with the same `ConnectionAccepted` again, same number, same token and same pack, at most once per 250 ms per player (half the 500 ms between two requests, so a request whose acceptance was lost is not held back because it crossed the network faster than the one before); the requests in between get nothing.

A sender that did not prove its address, that is whose request carries no valid cookie, never gets more bytes than it sent: a challenge (33 bytes) is smaller than the smallest request (38), and so is a refusal (26). Only a request with a valid cookie gets a `ConnectionAccepted`, which takes 64 bytes: the cookie went to the address the request came from, so the acceptance goes to an address that proved it receives the datagrams of the server. QUIC lifts its own limit on what it sends an address once it has validated that address the same way (RFC 9000, section 8). Whoever sees the traffic of a player and replays its cookie gets at most four acceptances per second sent to that player, for the 20 s at most that the cookie stays valid.

A nickname is unique on the server: a request whose nickname a player already holds is refused with `NicknameTaken`, before the cookie is checked. Letters of the ASCII alphabet compare without regard to case (`Ace` and `ACE` are the same nickname), every other byte compares as it is, so `É` and `é` are two nicknames. A player whose seat is held (see [A session](#a-session)) still holds its nickname; it is free again once the seat is. A sender already accepted is not refused as a duplicate of itself.

### Entity types

A type is named by the sheet it is read from (`assets/entities/drifter.toml` is `drifter`, see [Writing an entity sheet](/R-Type/entity-sheets/)), never by a number fixed in the code. The types of a server are the sheets of its [content pack](#content-pack), numbered in the order of their names, from 1; the server keeps those numbers while it runs, and `EntitySpawned`, `WorldState` and `DeltaWorldState` carry them. The first sheet is type 1, and 0 names no type. A client numbers the sheets of the pack the same way, and reads from each its `side` and its `[gameplay.hitbox]` (in `[gameplay]`) and its `[appearance]`, so it knows what an entity is, who it hits, where its own missile touches it and how to draw it, without the rest of the gameplay of the sheet. A number past the last sheet names nothing the client can draw: the client creates nothing for it.

### Content pack

The content of a server is what a client needs to draw the games it runs: every sheet of the `entities` folder of its assets, and every sprite sheet their `[appearance]` names (`sheet`), each kept once however many sheets name it. The server hands it over as one file, the content pack, named by its fingerprint. `ConnectionAccepted` announces the pack of the game in three fields:

| Field | Holds |
|---|---|
| `fingerprint` | the hash of every byte of the pack (below) |
| `size` | the bytes of the pack, 8388608 (8 MiB) at most; an acceptance that announces more is invalid |
| `port` | the TCP port the supervisor of the game serves the pack on, at the address the player joined; 0 when it serves none |

The payload of the `ConnectionAccepted` of player 1, byte by byte:

| Bytes | Field | Value |
|---|---|---|
| 0 | `playerNumber` | 1 |
| 1 to 32 | `fingerprint` | the 32 bytes of the fingerprint |
| 33 to 36 | `size` | the size of the pack |
| 37 and 38 | `port` | the port of the pack |

With its header and its message prefix, an acceptance takes 22 + 3 + 39 = 64 bytes, whatever the content of the server.

A client whose own assets make a pack of the same fingerprint plays at once with its own sheets. Any other client loads the pack of the server first: from its cache when it kept that pack, else by downloading it from the supervisor over HTTP (see [Downloading a pack](#downloading-a-pack)). Its session is open while the pack downloads: it holds its seat, sends its `Heartbeat`s, and shows in the waiting room of the others as a player not ready, so their game does not start without it. It plays once the pack has the announced size and fingerprint and its sheets can be read. Otherwise, or when `port` is 0 and no pack is kept, it sends its `Disconnection` three times with the token of the acceptance, as when a player leaves, so the server frees the seat at once, and it tells the player (see [Joining fails](#joining-fails)). A repeated acceptance changes nothing: the client loads the pack of the first one.

The pack, as fields in the encoding of this page:

| Field | Encoding | Holds |
|---|---|---|
| `format` | `u8` | 1 |
| `fileCount` | `u16` | 0 to 64 |
| then, per file, `path` | `string` | 1 to 64 bytes |
| `size` | `u32` | the bytes of the file |
| `bytes` | `size` bytes | the file, as it is on the disk |

- The files come in the strict order of their paths, byte by byte, so a path appears once, and the same assets always make the same pack and the same fingerprint.
- A path is relative to the assets folder, such as `entities/drifter.toml` or `sprites/mobs/reaper.png`: 1 to 64 characters of `a` to `z`, `0` to `9`, `_`, `.`, `/` and `-`, made of names separated by `/`, none of them empty, `.` or `..`, so a client that writes a file of a pack below a folder of its own never writes outside it.
- A file whose path is `entities/<name>.toml` is a sheet; every other file is a sprite sheet the sheets name.
- A pack holds at most 510 files (`MAXIMUM_CONTENT_PACK_FILES`, a sheet and a sprite sheet for each of the 255 types) and 8388608 bytes once encoded. A client built when the limit was 64 files refuses a larger pack.
- The `sheet` of every `[appearance]` of a pack names a file of that same pack: a client refuses a pack whose sheet names any other file.
- A reader refuses a pack larger than 8388608 bytes before reading it, and checks each count and each size against what remains before it copies a byte, so a pack never makes it read past the end or allocate more than the pack holds. It also refuses a pack of another `format`, one cut short, one with bytes after its last file, and one whose files break a rule above.

The fingerprint is the 32-byte hash of every byte of the encoded pack by `hydro_hash_hash()` of libhydrogen, without a key, in the context `rtpack01`. A path or a file name writes it as 64 lowercase hexadecimal digits. The content the game ships, 11 sheets and 5 sprite sheets, makes a pack of 26270 bytes.

#### Downloading a pack

A supervisor serves the pack of its assets folder over HTTP, on TCP, on every IPv4 interface, on the port of the same number as its UDP port. Its game processes run the same executable, so they read the same assets folder, and announce that pack and that port. A supervisor whose UDP port the system chooses serves no pack; one that cannot listen on the TCP port, held by another program, serves none either, while its games still announce the port, so a client that lacks the pack fails its download.

`GET /api/packs/{fingerprint}`, the fingerprint in lowercase hexadecimal, is open to everyone:

| Request | Answer |
|---|---|
| The fingerprint of the pack of the supervisor | 200, the pack as `application/octet-stream`, with the header `ETag` holding the fingerprint in quotes |
| The same, with a `Range` header | 206 and those bytes only |
| Any other fingerprint | 404, a problem document (RFC 9457) |
| More requests than the address may make | 429, a problem document, and nothing of the pack |

An address, whatever its port, may make 3 requests at once, then one every 10 s; 10 refused within a minute ban it for a minute. The pack is encoded once, when the supervisor starts, so what a request costs never depends on what it sends. TCP proves the address of the client before any byte of the pack goes out, so the route adds no amplification.

The client connects to the address the player joined, never to an address a datagram names, and to the `port` of the acceptance. A try that is cut asks again for the bytes from where it stopped (`Range: bytes=<received>-`, RFC 9110), 3 tries in all; each try waits at most 5 s to connect, then 5 s for each read or write. An answer of another status than 200 or 206, or more bytes than `size`, ends the download at once; a 200 to a resumed try starts the pack again. The client checks the size and the fingerprint of what came before it decodes it.

### Inputs

`actions` holds one bit per action, bit 0 being the least significant: 0 up, 1 down, 2 left, 3 right, 4 shoot. Bits 5 to 7 are 0, otherwise the message is invalid. A `PlayerInput` is sent even when no key is held (`actions` is 0). `inputNumber` starts at 1 and grows by 1 for each input sent. `shownTick` is the tick of the server the client draws the other entities at when it sends the input, 0 before its first state: the server tests the missiles of that player against the enemies where the player saw them (see [Own missiles](#own-missiles)).

A `PlayerInput` also repeats the inputs the server has not confirmed, so the loss of one datagram loses no input. `actions` is the newest input, numbered `inputNumber`; the `earlierCount` actions after it are those of the inputs numbered `inputNumber - 1`, `inputNumber - 2` and so on, newest first. `earlierCount` is at most 15 (`MAXIMUM_REPEATED_INPUTS`, **provisional**: 250 ms at 60 inputs per second, the time between two `WorldState` that confirm inputs plus a round trip, to be revised once measured on a real network) and never reaches below input 1: a message that announces more, or whose earliest input would be numbered 0 or less, is invalid. A sender repeats every input it sent that the server did not confirm, up to that limit; the server confirms an input in `acknowledgedInput` of `WorldState` (see [World state](#world-state)), which is the newest input it applied, so a client forgets the inputs numbered up to that value. Before any confirmation arrives, a sender repeats the 15 inputs before the newest.

The server keeps, for each player, the highest `inputNumber` it has seen. It reads a message from the oldest input to the newest and takes each one whose number is higher than that, so an input lost on its way is taken from the next message, once and in order, and one it already has changes nothing. It applies the newest input at every tick of a game in progress until a newer one arrives, and ignores an older one that arrives late.

`WorldState` lists every player and every entity of the game, in full each time. The payload of a state with one player and one entity, byte by byte:

| Field | Type |
|---|---|
| `tick` | `u32`, the simulation tick of the server, counted from the start of the game |
| `playerCount` | `u8` (1 to 4) |
| each player | `playerNumber` `u8`, `shipEntityId` `u32` (0 while the player has no ship), `lives` `u8`, `score` `u32`, `invulnerable` `bool`, `motion` `u8`, `acknowledgedInput` `u32` |
| `entityCount` | `u8` |
| each entity | `entityId` `u32`, `entityType` `u8`, `position`, `look` `u8` (see [Named effects and looks](#named-effects-and-looks)) |

`motion` says what the pilot does, one bit each from bit 0: the directions its newest `PlayerInput` holds, at their bits of `actions` (0 up, 1 down, 2 left, 3 right), then 4 its ship rolls, 5 its ship dashes. Bits 6 and 7 are 0, otherwise the message is invalid. `acknowledgedInput` is the `inputNumber` of the newest `PlayerInput` the server applied to the ship of the player, 0 while it applied none (an input the server holds before applying it is not confirmed yet, so the ship it reads is never ahead of the number): a client that predicts its own ship drops the inputs up to it and replays the others on top of the position it reads (see [Client](/R-Type/client/#own-ship-prediction-ownshippredictor-shipprediction)). The field was added to version 1 without changing `PROTOCOL_VERSION`, so two builds of version 1 may misread each other's states; version 2 has it from the start, so two programs of version 2 read the same states. A player takes 16 bytes and an entity 10, so one datagram holds up to 110 entities with 4 players. When the entities do not fit, the server sends several `WorldState` with the same `tick`, each in its own datagram, each with every player and a part of the entities. The client:

- ignores a `WorldState` whose `tick` is lower than the last one applied; an equal `tick` is another part of the same state. The `tick` is compared as a plain 32-bit integer, without wrap-around: it takes 2.27 years at 60 ticks per second to reach 2³². The sender checks come first, so a forged datagram cannot raise the last `tick` applied;
- creates an entity it does not know, from its type, with its appearance effect (the shot sound of a missile, for instance);
- removes an entity that no `WorldState` has listed for 900 ms, counted on the `tick` of the states. A state may come in several parts, and a later part may list an entity an earlier one left out, so a tick counts only once a part of a newer tick closes it: no later part of it is applied, and a lost part never comes. The entity goes when the tick 54 ticks or more past the last one that listed it is closed. With none lost, a ghost goes when the first state after the first state whose tick is 54 ticks or more past its last listing arrives: 950 ms after that listing at the default 20 states per second, 1000 ms at 10, 1500 ms at the lowest rate of 2. While no state arrives, nothing is removed.

An `EntityDestroyed` naming an entity the client does not know, and an `EntitySpawned` naming one it already has, change nothing.

Measured on October 24, 2026, before `acknowledgedInput` added 4 bytes per player, on a local game of two players lasting about 70 seconds (a `tcpdump` capture of the server port): each player received 20.0 `WorldState` per second, each state in a single datagram of 105 bytes of UDP payload on average and 116 at most, for 6 entities on average. That is about 2.1 kB per second and per player for the states alone. The players could not shoot yet, so the game held only ships and Bydos: a game with missiles sends larger states.

`entityId` is given by the server, unique during a game, and never 0. A `u16` would wrap after about 22 minutes at 50 new entities per second, hence 32 bits.

`entityType` is the number of a sheet of the content pack of the session (see [Entity types](#entity-types)). A `WorldState` or a `DeltaWorldState` may carry any number from 1 to 255: a state is read the same in every session, and what a number names is for the client to look up. An entity of type 0, which no type has, is skipped: it is left out of the state, and the other entities of the same `WorldState` are read. An entity takes 10 bytes whatever its type, so the next one starts where it should. A new kind of entity is a new sheet, and changes nothing on this page.

### Delta world state

`DeltaWorldState` is the state the server sends during a game: the same picture as a `WorldState`, written as the difference from an earlier state the player acknowledged, so an entity that did not move costs nothing. Its fixed part is 10 bytes, then the players and the two lists:

| Field | Type |
|---|---|
| `tick` | `u32`, as in a `WorldState` |
| `baseDistance` | `u8`, 0 to 60: how many ticks back the reference state was taken; 0 means no reference, and `changed` then lists every entity |
| `partIndex`, `partCount` | `u8` each: this datagram is part `partIndex` (from 0) of `partCount` (1 to 16) |
| players | `playerCount` `u8`, then each player as in a `WorldState`; every part lists them all |
| `changed` | `changedCount` `u8`, then each entity as in a `WorldState` (10 bytes): the entities the reference lacks, or whose position, rounded to an eighth of a unit, or look differs from it |
| `removed` | `removedCount` `u8`, then one `entityId` `u32` each: the entities the reference lists and this state does not |

The server keeps, for each player, the states it sent and the datagram sequence of each part. A state is acknowledged once the datagram of every one of its parts is, which the player says in the `acknowledgedSequence` and `acknowledgementBits` of its own datagrams (see [Datagram](#datagram)); the client acknowledges every datagram it accepts, so no message is added. The server writes a state against the newest state the player acknowledged, as long as it is 1 to 60 ticks older than the one it sends (1 s), and in full, with `baseDistance` 0, otherwise: the first state of a game, and the first after a second without an acknowledged state. It sends a delta even when nothing changed, with both lists empty, so the player keeps acknowledging. A state needing more than 16 datagrams is not sent, and the server logs an error.

The client:

- joins the parts of a tick, which may arrive in any order, and counts each part once. A part of a newer tick ends the wait for the parts missing from an older one, which the session refuses once a newer datagram was accepted, so they never come;
- writes the lists onto the state `baseDistance` ticks back, which it keeps for the last 60 states it rebuilt, and gives the rest of the client the full state, so everything after this point reads a state as it reads a `WorldState`: the rules of [World state](#world-state) above apply to the rebuilt state;
- drops a state whose reference it does not hold, with a warning. This does not happen while it accepts datagrams in order, since it keeps every state it rebuilds and the server only uses a reference whose every part the client accepted;
- forgets everything when the `tick` goes back, which is a game that started over.

Measured by `DeltaMeasurementTest` (`tests/server/Replication/Announcements/Streams/`), on ten seconds of a game with one player and 30 enemies, the player acknowledging every state at once, 20 states per second. A state in full takes 321 bytes with the headers, so states in full cost 6420 bytes per second:

| Enemies that move at every tick | Bytes per second to the player | Share of a state in full |
|---|---|---|
| 0 of 30 | 1047 | 16 % |
| 15 of 30 | 3733 | 58 % |
| 30 of 30 | 6420 | 100 % |

The gain comes only from the entities whose position did not change in the last state: an entity that moves costs 9 bytes in a delta as in a full state, so a game where everything moves at every state gains nothing, and one where half of the entities stand still saves about 40 %. `DeltaConvergenceTest` plays ten seconds over a network that loses one datagram in three and thirty in a row: every state the client rebuilds is the world at its tick, and the states after the outage are in full again.

### Game events

A `GameEvent` drives sounds and effects on the client, never a game rule. `eventNumber` starts at 1 for each game and grows by 1 for each event, wrapping from 65535 to 0; a copy sent again carries the same number. The ordered channel hands each event over once, so a receiver does not need the number to tell a copy.

| `kind` | Event | `playerNumber` | `entityId` |
|---|---|---|---|
| 1 | `EntityDamaged`: hit, still alive | 0 | the entity |
| 2 | `PlayerHit`: the player lost a life | the player | 0 |
| 3 | `PlayerEliminated`: no life left, the player now watches | the player | 0 |

An `EntityDamaged` naming an entity the client does not know changes nothing. The explosion of a ship that is hit comes from its `EntityDestroyed` (`Killed`).

A shot has no event of its own: a missile appears through the `EntitySpawned` of a type of side `PlayerMissile` or `EnemyMissile`.

### Boss status

A `BossStatus` tells where the fight with the boss of a level stands, so a client can warn the players and show its health. Each holds the whole state and replaces the one handed over before it; the ordered channel hands them over in the order sent, so the newest status is the newest state.

| `stage` | Sent when | `bossEntityId`, `health`, `fullHealth` |
|---|---|---|
| 1 `Arriving` | the last wave of a level with a boss is over; the boss appears 4400 ms later, through its `EntitySpawned` | 0, 0, 0 |
| 2 `Fighting` | the arrival of the boss is over, then at each hit that takes points from it | the boss, its points left, the points it appeared with |
| 3 `Enraged` | its health fell below its rage threshold, then at each hit that takes points from it | as `Fighting` |
| 4 `Defeated` | a hit took its last point, before its `EntityDestroyed` | the boss, 0, its full health |

A hit during the arrival takes nothing from the boss and sends nothing. The boss is an entity like any other: it moves through the states and is removed by its `EntityDestroyed`, and its attacks come as `EnemyAction`s. A client that receives a `Fighting` or an `Enraged` without an `Arriving` before it shows the fight from there. The time of the warning is not sent: a client counts it from the `Arriving` it received.

### Level status

A `LevelStatus` tells what the players see of the level a game plays (see [Server](/R-Type/server/#level-a-script-directs-leveldirector)): its `biome`, empty before the level names one, how far it scrolled, `scrollPosition`, in logical units, and the speed of its scroll, `scrollSpeed`, in logical units per second, 0 while the scroll is paused. Each holds the whole state and replaces the one handed over before it. Between two of them a client moves the scroll on at `scrollSpeed`, so it draws the decor of the biome without a message per tick. A game that plays its waves sends none.

### Named effects and looks

A sheet names effects and looks in its `[appearance]` (see [Entity sheets](/R-Type/entity-sheets/#named-effects-and-looks)), and a script of the server asks for one on a body. Both sides read the same sheets, from the content pack, so a name means the same frames on both.

- **An effect** plays once. The server sends an `EffectPlayed` with the `entityId` of the body and the name of the effect, guaranteed and ordered. The server sends only a name the sheet of the body holds, and at most one effect per body every quarter of a second, whatever its script asks for. A client that does not have the body, or whose sheet of that type names no such effect, plays nothing.
- **A look** lasts. It is a state, so it travels in every state message: `look` is the number of the look the body shows, its place among the looks of the sheet in the order of their names, from 1, or 0 for its own idle loop. A client that joins later, or loses a datagram, shows the right look at the next state. A client shows its idle loop for a number past the looks of the sheet.

### Own missiles

A client draws its own ship ahead of the server (it predicts it), and the other entities behind it (it interpolates them). A missile the server creates for that ship would show up a round trip late, behind the ship as the client draws it. So the client fires its own missile at once, from its predicted ship, and the server tells it which missile of the game is that one:

- `owner` is the number of the player whose ship fired the missile, `firingInput` the `inputNumber` of the newest `PlayerInput` the server had applied to that ship in the tick it fired. Both are 0 for anything else: a ship, a Bydo, a missile of an enemy, a shard.
- The server guarantees the `EntitySpawned` of a missile of a player, on the ordered channel (see [Ordered messages](#ordered-messages)), so the client always learns which input fired it. The others are sent once, as before.
- A client matches a missile it fired to the `EntitySpawned` whose `owner` is its own player number and whose `firingInput` is the input it fired with. What it draws of that missile, and when it gives up a shot the server did not make, is the business of the client (see [Client](/R-Type/client/)).

The client reads what it needs to fire as the server does from the sheets of the content it plays (see [Entity types](#entity-types)): the first ship of side `player` with a gun, the ticks between two shots and before the first one, and the velocity of its missile, in logical units per second. It predicts a missile only when that missile is of side `player_missile`, moves steadily and is piloted by `straight`, since only then is its path a straight line it can draw; otherwise, or when the sheets name a behaviour the client does not know (a pilot only a plugin of the server has), it predicts nothing and draws the missiles of its player as the server sends them.

Each `PlayerInput` says which tick the client shows the other entities at (`shownTick`). The server tests a missile of that player against the enemies as they were at that tick, so a missile hits what its player saw it hit; the server goes back at most 200 ms, and never hits an enemy that is already destroyed (see [Server](/R-Type/server/#lag-compensation-of-the-shots)). A client may claim any tick: the bound caps how far in the past it may make the server look, as every lag compensation does.

## A session

The messages of one session, from the connection to the end of a game:

```mermaid
sequenceDiagram
  accTitle: Messages of one session
  accDescr: The client asks to connect, receives a challenge, asks again with the cookie and is accepted. The server repeats the lobby state until every player is ready, then starts the game. During the game the client sends its inputs and the server sends world states and events. When the game ends, by a victory or because no player has a life left, the server repeats the end of the game, then the lobby state again.
  participant C as Client
  participant S as Server
  C->>S: ConnectionRequest (cookie 0)
  S->>C: ConnectionChallenge (cookie)
  C->>S: ConnectionRequest (cookie)
  S->>C: ConnectionAccepted (content pack)
  S->>C: LobbyState (repeated)
  C->>S: ReadyState
  S->>C: GameStarted
  C->>S: GameLoaded, PlayerInput (60 per second)
  S->>C: WorldState (20 per second by default), events
  S->>C: GameEnded (repeated)
  S->>C: LobbyState (repeated)
  C->>S: Disconnection
```

In each phase the server repeats one message, and the client shows the screen of the last one it received, so a lost transition never leaves it on the wrong screen; the end screen is the one exception (below).

| Phase | Repeated message | The client shows |
|---|---|---|
| Waiting for players | `LobbyState`, every 500 ms | the lobby |
| Game in progress | `WorldState`, 20 per second by default | the game |
| Game ended | `GameEnded`, every 500 ms | the end screen |

The end screen stays until the player chooses, whatever the server sends after `GameEnded`: a player who plays again finds the waiting room, a player who quits leaves the server. Between `GameEnded` and the next `GameStarted`, the server must send no `WorldState`: the client reads a `WorldState` as the start of a game.

The server takes a `ReadyState` into account only in the first phase, from a connected player, with the same checks as every datagram: the session token, then the `sequence`. Once at least one player is connected and every connected player is ready, the server sends `GameStarted` and waits for the clients to show the game: the screen of a client that has the game assets to load is not ready on the tick the server sends it. A client that shows the game sends `GameLoaded` with its inputs, at most every 100 ms, until the first `WorldState` arrives. The game starts, and the first `WorldState` goes out, once every connected player that is not away has sent one, or after 10 s (`START_BARRIER_SECONDS`) without waiting any longer for the others. Until then the server sends no `WorldState`, and repeats `GameStarted` every 500 ms to the players not yet loaded. A `GameLoaded` outside this wait changes nothing. The message is new in version 1 and carries no field; a server that does not know it skips it as an unknown type.

Each side sends a `Heartbeat` every 500 ms, whatever else it sends, and the client one more to acknowledge guaranteed messages (see [Guaranteed messages](#ordered-messages)); any datagram that passes the checks above proves its sender is alive. A player the server has heard nothing from for `SESSION_TIMEOUT` (5 s) may only have lost the network for a moment. The server then marks the player away and keeps its seat, its token, its ship, its score and its lives for `RECONNECTION_GRACE` (15 s) more. The ship stays in the world and can be hit, but the input of the player is cleared and the player does not count when the waiting room checks that everyone is ready. Any datagram carrying the token, from the same address and port, ends the absence: the player is back, nothing was lost, and a new `SESSION_TIMEOUT` starts. A player not heard from for `SESSION_TIMEOUT` plus `RECONNECTION_GRACE` (20 s) loses its seat: the server closes the session, removes the ship and sends `PlayerLeft` (`TimedOut`) to the others, only then. A client that comes back from another address or port is an unknown sender and starts again from the first request. The client keeps its session, and keeps sending its `Heartbeat`, for the same 20 s without a datagram from the server, then closes it and must tell the player that the connection is lost. A `Disconnection` frees the place at once, and the others get `PlayerLeft` (`Left`).

## Round trip

Each side measures the round trip of the session from the `Heartbeat`s, without a clock shared with its peer. A `Heartbeat` carries `sentAt`, the time it leaves on the clock of its sender, in microseconds modulo 2^32, and the echo of the newest `Heartbeat` its sender received: that one's `sentAt`, unchanged, and `echo.heldFor`, the microseconds from its arrival to this sending. When an echo comes back, the round trip is the time since the echoed `Heartbeat` left, read on the clock of the side that sent it, less `echo.heldFor`. A receiver dates each datagram as its socket hands it over, so the time a datagram waits for the next frame or tick counts as held, and is left out. An echo that gives a round trip below 0 or above 20 s is ignored, and a `Heartbeat` received more than 20 s earlier is no longer echoed.

Each side smooths its round trips, each one moving the estimate by an eighth of its gap to it, and takes as the jitter the mean gap between two round trips in a row over the 16 newest, 8 s of `Heartbeat`s. Right after each of its `Heartbeat`s, the server sends the player `RoundTrips`: the smoothed round trip and the jitter, in microseconds, of each player of the game it measured; a player not measured yet is not listed.

## Clock of the server

The two machines share no clock, so a client cannot tell at which of its own instants the server was at a given tick. The `Heartbeat` of the server answers it: while a game is in progress, `ticks` is 1 and `tick` is the tick the server is simulating when it sends it, the tick of the `WorldState` it sends in the same tick; outside a game the tick stands still, so `ticks` is 0 and `tick` is 0. A client never sets them.

A client that receives such a `Heartbeat` in a session, together with a round trip that its echo closes, may place that tick on its own clock. The server sent it half a round trip before the datagram arrived, so tick 0 stood at the arrival time, less half the round trip, less `tick` ticks of 1/60 s. The client keeps the 8 newest estimates, follows the one with the shortest round trip, as the clock filter of NTP does ([RFC 5905](https://www.rfc-editor.org/rfc/rfc5905)): a datagram that waited in a queue has a long round trip and is left aside. It moves toward that estimate by an eighth of the gap at each estimate, and jumps onto it when the gap is more than 6 ticks, and when a `tick` is lower than the previous one, which is a new game. The estimate is exact when the two ways of the path last the same; a path whose ways differ by some time moves it by half of that time, and nothing in the protocol can tell. This is a rule of the client of this repository, not a requirement on the wire: the protocol only says what the two fields mean.

## Errors

This section gathers what each side does when something goes wrong, from a datagram it cannot read to a peer that disappears. Most rules are stated in the sections above, which the tables link to; the rest are stated here. Three rules hold for every case:

- Nothing in a datagram stops a program or closes a session: an error ends with a datagram or a message dropped, never with a crash.
- A dropped datagram or message gets no answer, with one exception: the server answers a datagram of another version from an unknown sender with `ConnectionRefused` (`IncompatibleVersion`), under the size condition of [Receiving a datagram](#receiving-a-datagram).
- A dropped datagram or message changes nothing in the session or the game: at most, the receiver logs it and counts it, and the server counts one dropped for its rate limit against its sender (see [A sender that sends too much](#a-sender-that-sends-too-much)).

### A datagram or a message that cannot be read

| The receiver gets | It | It sends back |
|---|---|---|
| A datagram that fails one of the first checks of [Receiving a datagram](#receiving-a-datagram): size, `protocolId`, `flags`, message sizes | drops the datagram | nothing |
| A datagram of another `version` | drops the datagram; a client connecting to the server that sent it ends the attempt and tells the player both version numbers, its own and the one at offset 4 | from the server to an unknown sender, `ConnectionRefused` (`IncompatibleVersion`), under the size condition of [Receiving a datagram](#receiving-a-datagram); otherwise nothing |
| A datagram from an unknown sender that holds neither a `ConnectionRequest`, a `ServerInformationRequest` nor a `MasterProbe` | drops the datagram | nothing |
| Within a session, another `sessionToken`, or a `sequence` that is not newer | drops the datagram; a wrong token is counted | nothing |
| A message of an unknown type | skips that message and reads the next one | nothing |
| A message of a type that only the other side receives, such as `ConnectionAccepted` reaching the server or `PlayerInput` reaching a client | skips that message, as if its type were unknown | nothing |
| A payload of the wrong size, or a value out of range: a `bool` other than 0 or 1, an enumeration value not listed, a bit 5 to 7 set in `actions`, a bit 6 or 7 set in `motion`, a nickname that is empty, longer than 16 bytes, not UTF-8 or holding a control character (U+0000 to U+001F, U+007F) | drops that message; the other messages of the datagram are read | nothing, even to a `ConnectionRequest` dropped this way |
| An entity of type 0 in a `WorldState` or a `DeltaWorldState` | skips that entity and reads the next one (see [World state](#world-state)) | nothing |
| An `EntitySpawned` or an entity of a state whose type is past the last sheet of the pack of the session | the client creates nothing for it (see [Entity types](#entity-types)) | nothing |

### Supervisor

A supervisor (`r-type_server`, or `--mode supervisor`) starts a game process (`--mode game`) per game and sends each player to one. Four messages carry it. The datagram of a `ConnectionRedirect` is 27 bytes, never more than the 38 bytes of the smallest `ConnectionRequest` it answers, so it adds no amplification.

| Type | Message | Payload | Sent |
|---|---|---|---|
| 26 | `ConnectionRedirect` | `port` `u16` (1 to 65535) | supervisor to player, in answer to a request with a valid cookie |
| 27 | `GameStatus` | `state` `u8`: 1 waiting for players, 2 in progress, 3 finished; `nicknameCount` `u8` (0 to 4), then each `nickname` `string`, in the order of the player numbers; `measures` `u8`, one bit per measure that follows; then each measure the bits announce, a `u32` in microseconds, in the order of the bits: bit 0 the median duration of a tick, bit 1 its 95th percentile, bit 2 the mean round trip to the players | game process to supervisor, every second and when any field changes |
| 28 | `GameStatusAcknowledged` | none | supervisor to game process, in answer to each `GameStatus` |
| 33 | `ExpulsionOrder` | `nickname` `string` (1 to 16 bytes) | supervisor to game process, three times, when the host types `kick` in its console; the game expels every player of that nickname, the case of the ASCII letters aside, and a copy that finds none does nothing |

#### Creating, joining and leaving a game

A player says which game it wants in every `ConnectionRequest` it sends, the ones after a redirect included: `AnyGame` (number 0), whatever game has a free seat; `ExistingGame` with the number of a game, as the master lists them (`GAME 1` is number 1); or `NewGame` (number 0), a game of its own. Only a request with a valid cookie is placed, so a forged address opens nothing. The supervisor counts the seats of a game as its players plus the seats it already gave to players it sent there (see [Server](/R-Type/server/#supervisor-and-game-processes)), and a game still starting counts as one that waits for players: the player then gets no answer until the game reported, and asks again 500 ms later.

| The request asks for | The supervisor |
|---|---|
| `AnyGame` | sends the player to the game that already holds its seat, else to the first game played by the default rules that waits for players and has a free seat, a game opened for a `NewGame` of the default rules included; else starts a game of the default rules while fewer than 8 run; else refuses with `ServerFull` |
| `NewGame` | refuses with `UnknownDifficulty` when its waves file has no table of that `difficulty`, then with `LivesOutOfRange` when `lives` is not 1 to 9; else sends the player to the game its own `NewGame` opened, while that game waits for players and the player still holds its seat there or nobody else came, so a request repeated every 500 ms opens one game; else starts a game while fewer than 8 run; else refuses with `ServerFull` |
| `ExistingGame` | refuses with `GameNotFound` when no game has that number, with `GameInProgress` when it is in progress or finished, then with `GameFull` when it has no free seat and none held for the player; else sends the player to it, whatever its rules |

The rules of a game are fixed when it is opened, and apply to that game only. The default rules are the difficulty `normal`, 3 lives and no friendly fire; a client that lets its player choose none sends them with its `NewGame`. The difficulties a supervisor accepts are the tables of its waves file, which it reads when it starts and lists to the master with the rules of each game (see [Master](/R-Type/master/#listing-the-games-of-a-server)). The lives are **provisional**, 1 to 9 (`LOWEST_LIVES`, `HIGHEST_LIVES` in `src/identifiers/GameRuleConstants.hpp`), until gameplay tunes them. Friendly fire lets a missile of a player cost another player a life, never the player who fired it.

A game opened for a `NewGame` belongs to nobody: any player may join it, by its number, or with `AnyGame` when it is played by the default rules, and it starts as every game does, when all its connected players are ready (see [A session](#a-session)). Leaving a game is the `Disconnection` the player sends three times (see [A peer disappears](#a-peer-disappears)): nothing else is needed, and a game nobody joined ends on its own. The supervisor does no matchmaking: it never weighs players, pings or levels, it only fills seats in order. A game process reads the choice and the rules of a request and ignores them, since the supervisor already chose its game and gave it its rules.

A client that receives a `ConnectionRedirect` while it connects, and only the first one of an attempt, to a port other than the one it uses, sends its next request to that port with the cookie back at 0: the game draws its own cookies. The 5 s of the attempt do not restart. In any other state it ignores the message. Between the supervisor and a game process, the header carries the link token as `sessionToken`, and `sequence` orders the statuses.

### A sender that sends too much

The server limits what each sender may send, so that one sender cannot crowd out the others. After a silence, a sender may send a burst at once, then at a steady rate:

| Datagrams | At once | Then | Banned after |
|---|---|---|---|
| holding a `ConnectionRequest`, a `ServerInformationRequest` or a `MasterProbe`, whatever its token, or of another `version`, from one address and port | 11 | 4 a second | 20 dropped within a second |
| carrying the session token of a player, without a `ConnectionRequest` | 60 | 120 a second | 60 dropped within a second |

A datagram past its limit is dropped without an answer. A ban lasts 10 s: every datagram of that kind from that sender is dropped until then, and sending more does not lengthen it. A client that keeps to this page stays below these limits: it sends a request every 500 ms and the answer to each challenge, after a stall of the server the answers to the ten requests of its attempt at once, and 60 inputs a second during a game. The datagrams of a banned player never reach its session, so the server marks the player away after `SESSION_TIMEOUT` (5 s) and keeps its seat, since the ban ends before the 20 s that free it. Whoever uses the address of a player without its token never spends the limit of the player: a `ConnectionRequest` spends the limit of that address, and any other datagram is dropped before any limit. These values are **provisional**, and follow from the rates of this page: the server derives them from the interval between two requests, the 5 s of an attempt and the 60 inputs a second (`src/network/Handshake/RateLimit/RateLimitConstants.hpp`). Code must read them.

### A message at the wrong moment

A message that is valid but means nothing in the current state of its receiver changes nothing and gets no answer.

| The receiver gets | Because | It |
|---|---|---|
| `ConnectionChallenge`, `ConnectionAccepted` or `ConnectionRefused`, on a client that is not connecting | the attempt was already accepted, refused or given up | ignores it |
| `ConnectionRequest` from a player already accepted | its acceptance was lost | answers it as [Connection](#connection) says: the same `ConnectionAccepted` with a valid cookie, at most once per 250 ms, a `ConnectionChallenge` without one |
| `ReadyState` while no game waits for players | the game has started or ended | ignores it (see [A session](#a-session)) |
| `PlayerInput` while no game runs | the player holds keys before the start | keeps it as the newest input of that player, like any other (see [Inputs](#inputs)) |
| A `LeaderboardRequest` less than 500 ms after the last one answered | the client asked again, or floods | ignores it (see [Leaderboard](#leaderboard)) |
| A `ServerInformation` a client did not ask for | it came late, or was forged | skips it, as a message only the server receives would be |
| `WorldState` with a `tick` lower than the last one applied | it arrived late | ignores it (see [World state](#world-state)) |
| `EntitySpawned` naming an entity the client has; `EntityDestroyed` or `EntityDamaged` naming one it does not have | a copy, or a `WorldState` came first | changes nothing |
| A `ChatLine` whose number is not newer than the last line relayed for that player, or less than 1 s after it | a copy, or a flood | ignores it (see [Chat](#chat)) |
| A `ShipLookChoice` less than 100 ms after the last one taken, or during a game | a copy, a flood, or a late message | ignores it (see [Ship looks](#ship-looks)) |
| A second copy of an `OrderedMessage` (same `number`) | the acknowledgement of a datagram that held it was lost, so it was sent again (see [Ordered messages](#ordered-messages)) | ignored: the number was handled |

### Joining fails

| What happens | The client | The player is told |
|---|---|---|
| No answer within 5 s of the first request: no server at that address, a firewall, or every request or answer lost | stops sending requests | that the server is unreachable |
| `ConnectionChallenge`, because the cookie is missing, wrong or expired | sends the request again with that cookie; the 5 s are not restarted | nothing yet: the attempt goes on |
| `ConnectionRefused` (`GameFull`) | stops sending requests | that the game is full |
| `ConnectionRefused` (`GameInProgress`) | stops sending requests | that a game is in progress |
| `ConnectionRefused` (`NicknameTaken`) | stops sending requests | that the callsign is taken |
| `ConnectionRefused` (`GameNotFound`), from a supervisor: the request named a game it does not run | stops sending requests | that no such game exists |
| `ConnectionRefused` (`ServerFull`), from a supervisor: 8 games run, and none has a seat for an `AnyGame`, or a `NewGame` needs a ninth | stops sending requests | that the server is full |
| `ConnectionRefused` (`UnknownDifficulty`), from a supervisor: the `NewGame` names a difficulty its waves file has no table for | stops sending requests | that no such difficulty exists |
| `ConnectionRefused` (`LivesOutOfRange`), from a supervisor: the `NewGame` gives fewer than 1 or more than 9 lives | stops sending requests | that the lives are out of range |
| `ConnectionRefused` (`IncompatibleVersion`) | stops sending requests | both version numbers |
| `ConnectionAccepted` of a pack the client neither has nor keeps, from a supervisor that serves none (`port` 0) | opens no session, sends its `Disconnection` three times with the token of the acceptance, and stops sending requests | that the download of the pack failed |
| The download of the pack fails: nothing listens on the TCP port, the tries are cut 3 times, or an answer of another status or larger than announced | leaves the session, sending its `Disconnection` three times | that the download of the pack failed |
| The pack came, but has another size or fingerprint than announced, or holds a sheet the client cannot read | leaves the session the same way, and keeps nothing of the pack | that the pack was refused |
| A request the server drops, such as one with an invalid nickname | gets no answer, so it ends as unreachable after 5 s | that the server is unreachable |

### A peer disappears

| What happens | Who notices, and how | What follows |
|---|---|---|
| The player closes the client | the server, from the `Disconnection`, sent three times | the place is freed at once; the other players get `PlayerLeft` (`Left`) |
| The client loses the network for less than 20 s, or stops sending for that long | the server, after 5 s without a datagram carrying the token of that player | the player is away: the seat and the ship stay; the first datagram that carries the token, from the same address and port, gives the player back |
| The client crashes, is killed, or stays silent for 20 s | the server, after 5 s without a datagram carrying the token of that player, then 15 s more | the session closes and the ship is removed; the other players get `PlayerLeft` (`TimedOut`) |
| The server shuts down | each client, from the `Disconnection`, sent three times | the client closes the session at once and tells the player that the server closed it |
| The host expels a player | the game process, from the `ExpulsionOrder` of its supervisor; then the player, from the `Expulsion`, sent three times | the player closes the session at once and tells the player that the host expelled it; the game closes the session at its next tick, the others get `PlayerLeft` (`Expelled`). The player may join again: an expulsion bans nobody |
| The server crashes, is killed or loses the network | each client, after 20 s without a datagram from the server | the client closes the session and tells the player that the connection is lost |

A player that comes back after its session closed, 20 s after its last datagram, connects again from the first request, as an unknown sender, and gets a new session token.

The programs handle every case above. In a game, a `PlayerLeft` marks its pilot on the status band and writes a line on the screen of the others (see [Client](/R-Type/client/#departures-and-a-silent-server-departurefeed-silencewarning)). The `Disconnection` the server sends three times when it shuts down on Ctrl-C or SIGTERM (see [Server](/R-Type/server/#stopping-ctrl-c-and-sigterm)), an `Expulsion` from a game whose host typed `kick` (see [Server](/R-Type/server/#expelling-a-pilot)), or 20 s without a datagram of the server, ends the session of the client, which goes back to its title and says so in a dialog (see [Client](/R-Type/client/#lost-connection-a-dialog-over-the-title)). While the client holds the session without hearing the server, a game says so (`WAITING FOR THE SERVER`); the waiting room and the end screen do not.

## Ordered messages

`EntityDestroyed`, `EnemyAction`, `GameEvent`, `PlayerLeft`, `PlayerChatLine`, `BossStatus`, `PlayerLooks`, `LookItemWon`, `EffectPlayed` and `LevelStatus` change the screen once, and no state message repeats what they show, so they are guaranteed and ordered: their sender sends them again until they are acknowledged, and their receiver handles them in the order they were given, so a player never dies on the screen before the hit that killed it. In this version only the server sends them, and only the client acknowledges them.

- **Acknowledging.** Within a session, every datagram a side sends MUST acknowledge the datagrams it accepted from its peer, with `ACKNOWLEDGES`, `acknowledgedSequence` and `acknowledgementBits` (see [Datagram](#datagram)). A side that accepts a datagram with `GUARANTEED` set SHOULD send a `Heartbeat` to carry the acknowledgement when 40 ms (`ACKNOWLEDGEMENT_DELAY`) pass with nothing else sent; during a game the next `PlayerInput` carries it first.
- **Numbering.** The server sends each of these messages to each player inside an `OrderedMessage` (type 23): `number` (`u16`), `firstKept` (`u16`), `innerType` (`u8`), then the payload of the message it carries, to the end of the payload. The numbers of a player start at 1 (`FIRST_ORDERED_NUMBER`) and grow by 1 for each message given to that player, wrapping from 65535 to 0. A receiver MUST refuse an `OrderedMessage` that carries an `OrderedMessage`, whose `firstKept` is later than its `number`, or whose carried payload is over 1170 bytes (`ORDERED_PAYLOAD_LIMIT`). The envelope adds 5 bytes to a message.
- **Sending again.** The server sends the message at once, in a datagram with `GUARANTEED` set, and keeps it for each player until an acknowledgement names one of the datagrams it went in. While it is not acknowledged, the server sends it again once 100 ms (`GUARANTEED_RESEND_DELAY`) passed since its last send, in a new datagram with a new sequence and `GUARANTEED` set; the messages due to one player go together, as many as fit in 1200 bytes. A message only goes to the players of the game when it is given: a player who joins later never gets it.
- **Handing over in order.** A receiver handles the messages of the channel by number, once each. It keeps a message that arrives before the ones numbered under it, up to `ORDERED_WINDOW` (256) numbers ahead of the next one it expects, and ignores a number it already handled, or farther ahead. Only this channel waits: every other message of a datagram, the states included, is handled as it arrives.
- **Giving up.** The server drops a message 1 s (`GUARANTEED_MESSAGE_LIFETIME`) after it was given, acknowledged or not, and also when 256 more numbers were given after it: by then the client removed an entity no state lists (900 ms), and a sound would come too late. `firstKept` is the number of the first message the server has not given up; every envelope carries it. A receiver that expects a number before `firstKept` stops waiting: it handles the messages it holds under `firstKept`, in order, and expects `firstKept` next. The server counts the time in real time at the start of each tick and sends again at the end of a tick: at 60 ticks per second, every 7 ticks (116.7 ms), 9 times at most. With 20 % of datagrams lost independently, about one message in two million (0.2 to the 9th) is given up, and the order holds until then.
- **Reading once.** The number tells a copy the server sent again from the message: a receiver handles each number once, so the client no longer remembers the `eventNumber` of the events it saw.

Alternative considered: a number in each of the three messages. It adds the same bytes, but changes three layouts, and a message made ordered later would have to change its own. The envelope leaves the three messages as they were.

Alternative considered: never giving up an ordered message. The order would hold whatever the losses, but a player silent for a few seconds would get every event it missed, in order, with sounds and explosions long late, and the server would have to keep them all. Giving up after 1 s keeps what the screen shows current, at the price of the order after 1 s of losses.

Alternative considered: `Disconnection` guaranteed as well. Its sender closes at once and cannot wait for an acknowledgement, so it keeps its three copies, as netcode.io sends its disconnect packets without waiting for an answer.

## Losses

Only the messages of [Ordered messages](#ordered-messages) are sent again until they are acknowledged. The state messages are repeated, so the other losses correct themselves.

`Disconnection` changes the screen once too, but its sender closes at once, so it is sent three times, 50 ms apart. A copy that arrives after the first comes from a session already closed, so from an unknown sender, and changes nothing. With 5 % of datagrams lost independently, one `Disconnection` in 8000 is lost for good.

| Lost message | Corrected by | Within |
|---|---|---|
| `ConnectionRequest`, or its answer, the announcement of the content pack included | the client sends the request again, the server answers it again, an acceptance at most once per 250 ms | 500 ms |
| `ReadyState` | sent again while `LobbyState` shows another value | 500 ms |
| `LobbyState`, `GameEnded` | the next one | 500 ms |
| `WorldState`, `DeltaWorldState` | the next one; a delta lost is not a reference, so the next is written against an older acknowledged state, or in full after a second without one | 50 ms at the default 20 per second, one rate-th of a second at any other |
| `GameStarted` | the copy sent every 500 ms, or the first state | 500 ms |
| `GameLoaded` | the next one, sent with an input | 100 ms |
| `LeaderboardRequest`, or its answer | the client sends the request again, the server answers it again | 500 ms |
| `PlayerInput` | the next input, which repeats it until the server confirms it | 17 ms |
| `Heartbeat` | the next one, whose echo measures the round trip again | 500 ms |
| `ChatLine` | the next copy | 500 ms |
| `ShipLookChoice` | the next copy, sent until a `PlayerLooks` shows the look | 500 ms |

| every send of a `BossStatus` | the next `BossStatus`, which holds the whole state: a lost `Arriving` shows no warning, and the fight shows from its first status that arrives; a lost `Defeated` has none after it, so the client keeps the last health until the game screen closes | the next hit, rage or death of the boss |

The rates and delays on this page (60 inputs and 20 states per second by default, 40 ms, 100 ms, 250 ms, 500 ms, 900 ms, 1 s, 5 s, 15 s, 20 s, the 10-second cookie window, and the eighth and the 16 round trips of [Round trip](#round-trip)) are **provisional**: they will be revised once measured on a real network. Code must name each of them as a constant and never repeat the number.

## Compression

From version 4, the server may send the body of a datagram, the bytes after the 22-byte header, as one zstd frame. The client reads the frame back before anything else reads the datagram, so no message changes.

- `COMPRESSED` (0x04) in `flags` says that the body is a zstd frame. The flag belongs to the transport: the receiver clears it once the body is decoded, so a header that still holds it is refused by the `flags` check of [Receiving a datagram](#receiving-a-datagram).
- Only the server compresses, and only a datagram it sends within a session (`sessionToken` is not 0). `ConnectionChallenge` and `ConnectionRefused` stay readable by a peer of any version, with the size the handshake counts on, and `ServerInformation`, sent outside a session too, keeps the size that makes it no larger than its request (see [Server information](#server-information)). What a supervisor and its games send each other (`GameStatus`, `GameStatusAcknowledged`, `Disconnection`, `ExpulsionOrder`) stays plain, since a server drops what it receives compressed. The client to server direction is never compressed: its datagrams are about 30 bytes, and the server then never decodes data from an untrusted sender.
- A sender uses the compressed form only when it is strictly shorter than the original body, so a datagram never grows.
- Every frame is made with the dictionary of the protocol (2048 bytes, `assets/compression/server_to_client.dict`), at zstd level 1, without checksum, content size or dictionary identifier. The dictionary is part of the protocol: changing it changes `version`.
- A client decodes into a buffer of at most 1178 bytes (`MAXIMUM_BODY_SIZE`, the datagram less its header) with a decoder window of 2 KiB, so a forged frame allocates nothing from a value it carries. It drops the datagram, without answering, when the token is 0, when the frame is cut, corrupt or followed by other bytes, or when it decodes to more than 1178 bytes. A server drops every datagram it receives with the flag raised.
- A forger of the address of the server gets nothing from this: the client keeps no state while decoding and answers nothing, and the token is checked afterward as for any datagram.

On the games captured while the dictionary was trained, the datagram of the server is 25.1 % shorter with level 1 (23.9 % with level 3).

## Versions and compatibility

A program speaks one version of the protocol, the number at offset 4 of every datagram it sends. This section says what stays the same in every version, which changes give the protocol a new number, and what two programs of different versions do when they meet. The sections after it apply these rules to each version, from version 2 to version 16.

### What never changes

- `protocolId` stays at offset 0 and `version` at offset 4, in every version, so a receiver of any version reads from the first 5 bytes of a datagram which protocol and which version sent it.
- A type byte keeps its message. A number of the [message tables](#messages) is never given to another message, even once its message is no longer sent: the server no longer sends `WorldState` (type 10), and a client still reads it.
- A value of an enumeration keeps its meaning: `ConnectionRefused` reason 3 is `IncompatibleVersion` in every version, and a new value takes the next free number.

### What changes the version

`version` MUST grow by 1 when a change makes a receiver of the version before read a datagram wrongly, or drop a message it needs:

| Change | Example |
|---|---|
| A field added to, removed from or moved in the header or a message that already exists | `GameEnded` gains `outcome` before `playerCount` (version 3); `PlayerInput` repeats earlier inputs (version 5); `ConnectionRequest` gains `kind` and `number` (version 9); `ConnectionAccepted` announces the content pack (version 10); `EntitySpawned` gains `owner` and `firingInput`, `PlayerInput` gains `shownTick` (version 11); `ConnectionRequest` of kind `NewGame` gains `difficulty`, `lives` and `friendlyFire` (version 12); each entity of `WorldState` and `DeltaWorldState` gains `look` (version 16) |
| A field that keeps its place and changes its meaning | the acknowledgement fields of the header, written as 0 before (version 2); `entityType` read from a table (version 6) |
| A flag or an encoding of the body a receiver of the version before cannot read | `COMPRESSED` (version 4) |
| A message that already exists moved into an envelope | `EntityDestroyed`, `EnemyAction`, `GameEvent` and `PlayerLeft` inside `OrderedMessage` (version 7) |
| A new value of an enumeration of a message that already exists | a receiver of the version before drops the whole message as out of range (see [Payload rules](#payload-rules)): `ConnectionRefused` gains `GameNotFound` and `ServerFull` (version 9); `PlayerLeft` gains `Expelled` (version 13); `ConnectionRefused`, `Expulsion` and `PlayerLeft` gain `Banned` (version 14), then lose it (version 15) |

A message between a game process and its supervisor counts too: `GameStatus` gained the nicknames and the measures in version 8.

### What keeps the version

- **A new message type.** A receiver that does not know a type skips that message and reads the next one (see [A datagram or a message that cannot be read](#a-datagram-or-a-message-that-cannot-be-read)), so a new type MAY be added without changing `version`, on one condition: a peer that does not know it still plays, and loses at most what the message adds. `EnemyAction` (type 22) only loses the animation of an attack; `ChatLine` and `PlayerChatLine` (types 30 and 31) only lose the chat. When the new message replaces one a peer needs, the sender MUST keep sending the old one, or `version` changes: see the case of `DeltaWorldState` in [Version 3](#version-3).
- **A new message outside any session.** `ServerInformationRequest`, `ServerInformation` (types 24 and 25) and `MasterProbe` (type 29) did not change `version`: a server that does not know them drops them as datagrams of a sender it did not admit, and the asker gets no answer.
- **A change with nothing on the wire.** How a side measures, waits or limits, such as the client counting the losses of the server from the gaps in `sequence`, changes no byte.

Each new version gets a section below that says what changed and why `version` did, and each new message that kept the version is named in the section of the version it was added in, with what a peer that does not know it does.

### When two versions meet

- There is no negotiation. A program speaks exactly one version and drops every datagram of another (see [Receiving a datagram](#receiving-a-datagram)), so a client and a server of different versions never play together.
- The server answers a datagram of another version from an unknown sender with `ConnectionRefused` (`IncompatibleVersion`), written in its own version, if the datagram holds at least 26 bytes. A client that is connecting MUST read offset 4 of a datagram of another version from the server it contacts, before dropping it, end the attempt and SHOULD tell the player both numbers, its own and that of the server (see [Joining fails](#joining-fails)).
- A server registers its version with the master (see [Server](/R-Type/server/)). The server map of the client sends a `ServerInformationRequest` only to the servers of its own version, and SHOULD mark the others as needing an update, as it does, so a player knows before trying one that it cannot be joined.

## Version 2

Version 2 guarantees `EntityDestroyed`, `GameEvent` and `PlayerLeft` with `flags`, `acknowledgedSequence` and `acknowledgementBits`, which version 1 wrote as 0 (see [Ordered messages](#ordered-messages)). The layout of the header is the same, its meaning is not, so `version` became 2. The server also groups the guaranteed messages it sends again in one datagram, which receivers of version 1 already accepted.

Version 2 also gives `Heartbeat` the time it is sent and the echo of the newest `Heartbeat` received, which measure the round trip (see [Round trip](#round-trip)), then the tick of the server while a game runs (see [Clock of the server](#clock-of-the-server)). A build of version 2 from before the echo sends an empty `Heartbeat`, and one from before the tick stops at the echo, 13 bytes instead of 18: a newer receiver skips either as a message, and an older receiver skips the longer one, since bytes follow what it reads. In every case the datagram still keeps the session alive, so the two play together without a round trip or a clock.

## Version 3

Version 3 gives `GameEnded` the outcome of the game: `outcome`, one byte, comes first, before `playerCount` (see [Messages](#messages)). A game now has an end other than the loss of every life: it is won once the players beat the last wave of the level, so a client needs the outcome to tell a victory from a defeat. The layout of the other messages and of the header is the same; a payload of version 2 has no `outcome`, so its first byte would be read as one, which is why `version` became 3.

Three changes made while the protocol was at version 3 kept it there:

- The client measures the loss rate of the server from the gaps in `sequence`, as the server does for each player: nothing changes on the wire.
- States are sent as differences from the last one the player acknowledged, by a new message, `DeltaWorldState` (see [Delta world state](#delta-world-state)): `WorldState` is unchanged, so `version` did not change. The server then stopped sending `WorldState`, so a build of version 3 from before `DeltaWorldState` sees no world with a later server; under the rules of [Versions and compatibility](#versions-and-compatibility), `version` should have changed then. Every build of version 4 and later reads both.
- A server answers `ServerInformationRequest` with `ServerInformation`, two new messages (see [Server information](#server-information)): no message changed, so `version` did not change. A server of version 3 built before them drops the request of a stranger, as it drops any datagram that holds no `ConnectionRequest`.

## Version 4

Version 4 adds the `COMPRESSED` flag and the compression of the server's datagrams (see [Compression](#compression)). The layout of the header and of every message is the same. A client of version 3 would drop the compressed datagrams it cannot read, so `version` became 4 and the server answers a client of version 3 with `ConnectionRefused` (`IncompatibleVersion`).

## Version 5

Version 5 makes `PlayerInput` repeat the inputs the server has not confirmed (see [Inputs](#inputs)). The payload gains `earlierCount` and the earlier `actions` after the newest one, so `version` became 5 and a client and a server of different versions never play together. The datagram of an input with nothing to repeat is 31 bytes (22 + 3 + 6), one more than before, and 1 byte more for each input repeated. The confirmation travels in `acknowledgedInput`, which version 2 already sent.

## Version 6

Version 6 names the entity types by a table instead of four values fixed in the code: `ConnectionAccepted` carries `typeCount` and the types after `playerNumber`, and the `entityType` of `EntitySpawned`, `WorldState` and `DeltaWorldState` is a number of that table (see [Entity types](#entity-types)). The layout of `ConnectionAccepted` changes, and the meaning of `entityType` too: a receiver of version 5 would read type 1 as the ship of a player, which is why `version` became 6. An acceptance is now larger than the request it answers, which only a request with a valid cookie gets (see [Connection](#connection)).

`EnemyAction` (type 22) did not change `version`: a receiver that does not know it skips it as an unknown type, and only the animation of an attack is lost, so a client of version 6 without it plays with a server that sends it.

## Version 7

Version 7 sends `EntityDestroyed`, `EnemyAction`, `GameEvent` and `PlayerLeft` inside an `OrderedMessage` (type 23) and delivers them in the order they were given (see [Ordered messages](#ordered-messages)). The layout of the header and of every other message is the same. A client of version 6 would not read the envelope, so `version` became 7 and the server answers a client of version 6 with `ConnectionRefused` (`IncompatibleVersion`).

`ServerInformationRequest` and `ServerInformation` (types 24 and 25) did not change `version`: a server of version 7 that does not know them drops the request as a datagram from a sender that was not admitted and holds no connection request, and the asker gets no answer, as from a server that does not answer.

## Version 8

Version 8 makes a `GameStatus` say who plays the game and what its process measured: the nicknames of its players and up to three measures replace `playerCount` (see [Supervisor](#supervisor)). The supervisor reads from them the list of games it gives the master and the measures of the server, and counts the players and the free seats it answers an information request with, so a game process never talks to the master. A measure the process has not taken, before its first metrics report or without its metrics module, is left out, never sent as 0. A supervisor of version 7 would refuse every status of a game of version 8, whose bytes go on past `playerCount`, so `version` became 8, and the server answers a client of version 7 with `ConnectionRefused` (`IncompatibleVersion`). The layout of the header and of every other message is the same.

## Version 9

Version 9 lets a player create or join a game: `ConnectionRequest` carries `kind` and `number` after the nickname, and `ConnectionRefused` gains `GameNotFound` (5) and `ServerFull` (6) (see [Supervisor](#supervisor)). A supervisor now refuses an `AnyGame` with `ServerFull` where it answered `GameFull` when its 8 games ran full. The smallest request grows from 35 to 38 bytes, which keeps every answer to a sender that did not prove its address smaller than it. A server of version 8 would refuse every request of version 9 as having bytes after its nickname, so `version` became 9, and the server answers a client of version 8 with `ConnectionRefused` (`IncompatibleVersion`). The layout of the header and of every other message is the same.

`MasterProbe` (type 29) did not change `version`: a server of version 9 that does not know it drops it as a datagram from a sender that was not admitted and holds no connection request, sends no token back, and the master lists it as unreachable.

`ChatLine` and `PlayerChatLine` (types 30 and 31) did not change `version`: a peer that does not know them skips them, and the ordered channel hands a `PlayerChatLine` over to a client without the chat, which skips it, so the order of the channel holds.

`ShipLookChoice`, `PlayerLooks` and `LookItemWon` (types 35 to 37) did not change `version`: a peer that does not know them skips them. One consequence the version does not catch: an older client that downloads a content pack with a sheet of the side `look_item` cannot read it, so it cannot join a server that ships look items. Both programs are built from the same repository, so this is written here and not worked around.

`LevelStatus` (type 39) did not change `version`: a peer that does not know it skips it, and a client without it plays the level under the sky it has.

## Version 10

Version 10 makes `ConnectionAccepted` announce the content pack of the game, its fingerprint, size and port, in place of the table of its entity types (see [Content pack](#content-pack)), and adds the route of the pack, over HTTP. The types are still the sheets numbered from 1 in the order of their names, so `EntitySpawned`, `WorldState` and `DeltaWorldState` keep their layout and their meaning; what changes is where a client finds the sheets: in its own assets, its cache or the pack of the server, so a server with sheets the client lacks no longer turns it away. An acceptance now takes 64 bytes whatever the content, where it took up to 859. The layout of `ConnectionAccepted` changes, so `version` became 10, and the server answers a client of version 9 with `ConnectionRefused` (`IncompatibleVersion`). The layout of the header and of every other message is the same.

`BossStatus` (type 32) did not change `version`: the ordered channel hands it over to a client that does not know it, which skips it, so the order holds. Such a client plays the boss as any enemy, without its warning or its bar.

## Version 11

Version 11 lets a client predict its own missiles (see [Own missiles](#own-missiles)): `EntitySpawned` ends with `owner` and `firingInput`, and `PlayerInput` ends with `shownTick`. The layout of both messages changes, so `version` became 11, and the server answers a client of version 10 with `ConnectionRefused` (`IncompatibleVersion`). `ConnectionAccepted` keeps the layout of version 10: the client reads the box of each type and the gun of the ships from the sheets of the content it plays, as it already read their side. An `EntitySpawned` grows from 9 to 14 bytes, and a `PlayerInput` by 4. The server now guarantees the `EntitySpawned` of a missile of a player; the others are still sent once.

## Version 12

Version 12 lets the player who creates a game choose its rules: a `ConnectionRequest` of kind `NewGame` carries `difficulty`, `lives` and `friendlyFire` after `number`, and `ConnectionRefused` gains `UnknownDifficulty` (7) and `LivesOutOfRange` (8) (see [Supervisor](#supervisor)). A request of any other kind keeps its bytes, so the smallest request still takes 38 bytes and no answer to a sender that did not prove its address grows. A server of version 11 would refuse a `NewGame` of version 12 as having bytes after its number, so `version` became 12, and the server answers a client of version 11 with `ConnectionRefused` (`IncompatibleVersion`). The layout of the header and of every other message is the same.

## Version 13

Version 13 adds the expulsion of a player: `ExpulsionOrder` (type 33) from the supervisor to a game process, `Expulsion` (type 34) from the game to the player, and the departure reason `Expelled` (3) of `PlayerLeft` (see [Supervisor](#supervisor) and [A peer disappears](#a-peer-disappears)). A client of version 12 would refuse a `PlayerLeft` of reason 3 as an invalid value, and that message is guaranteed, so `version` became 13, and the server answers a client of version 12 with `ConnectionRefused` (`IncompatibleVersion`). The layout of the header and of every other message is the same.

A game reads an `ExpulsionOrder` only from its supervisor, at the loopback address and the port its link names, under the link token, checked on the network thread like the token of a player; a datagram of any other sender holding one is never read. A client reads an `Expulsion` only in its session, after the token and the sequence. Neither message is answered.

## Version 14

Version 14 added the ban of a player: the reason `Banned` of `ConnectionRefused` (9), of `Expulsion` (2) and of `PlayerLeft` (4). A client of version 13 would refuse a `PlayerLeft` of reason 4 as an invalid value, and that message is guaranteed, so `version` became 14. No message was added: the supervisor wrote its bans to the file of the server, which its games read again every second.

## Version 15

Version 15 removes the ban of a player, since the project keeps no accounts and a ban of a nickname or of an address is easy to get around: the reasons `Banned` of `ConnectionRefused` (9), of `Expulsion` (2) and of `PlayerLeft` (4) are invalid again, and a receiver drops a message that holds one as out of range (see [Payload rules](#payload-rules)). A server of version 14 could still send them, so `version` became 15, and the server answers a client of version 14 with `ConnectionRefused` (`IncompatibleVersion`). The expulsion of version 13 stays. The layout of the header and of every message is the same as in version 14.

## Version 16

Version 16 lets the content of a server draw visual effects without code on the client (see [Named effects and looks](#named-effects-and-looks)). Each entity of `WorldState` and `DeltaWorldState` gains `look`, 1 byte after `y`, so an entity takes 10 bytes instead of 9: a receiver of version 15 would read every entity after the first one at the wrong offset, so `version` became 16. A client of version 15 also refuses a content pack whose sheets hold `[appearance.effects]` or `[appearance.looks]`, an unknown key for it.

`EffectPlayed` (type 38) was added in the same version. Alone it would have kept `version`: a peer that does not know it skips it and only loses the effect.

## Implementation status

The code of this repository applies the rules above, with the exceptions listed at the end of this section.

- The socket of the server compresses what it sends within a session, and the socket of the client decodes it, as [Compression](#compression) describes (`src/network/Compression/`). The traffic counters read the datagram before compression and after decoding, so `--traffic-csv` counts the bytes of the plain datagrams, not the bytes on the wire.
- `src/network` holds the pieces: the socket in `Transport` drops a datagram over 1200 bytes (see [Network](/R-Type/network/)), `Serialization` encodes integers and strings, and `Protocol` holds the header and every message of this page, each checked as listed here. A `WorldState` without players is accepted while the game has none (see [Network](/R-Type/network/#world-state-worldstatecodec)).
- Both programs drop a datagram whose header is not of this protocol and version, or whose message sizes do not add up. The server drops on its network thread every datagram that is neither a connection request, an information request nor from a player it admitted, answers the requests as [Connection](#connection) and [Server information](#server-information) describe, and answers a datagram of another version from an unknown sender with `ConnectionRefused` (`IncompatibleVersion`). The client reads only the server it contacts.
- Within a session, each side writes the session token and its next sequence into every datagram it sends: the server in its acceptances, the `EntitySpawned` of the ships, the Bydos and the missiles, `LobbyState`, `GameStarted`, `DeltaWorldState`, the game events, `GameEnded`, `LeaderboardAnswer`, `Heartbeat`, `RoundTrips` and `Disconnection`; the client in its inputs, `ReadyState`, `GameLoaded`, `LeaderboardRequest`, `Heartbeat` and `Disconnection`. Each also acknowledges there the datagrams it accepted, except the client in its `Disconnection`, sent once the session is closed.
- The server sends `EntityDestroyed`, `EnemyAction`, `GameEvent`, `PlayerLeft`, `PlayerChatLine`, `BossStatus`, `PlayerLooks`, `LookItemWon`, `EffectPlayed` and `LevelStatus` as [Ordered messages](#ordered-messages) describes, and reads the acknowledgements of every datagram of a player it accepts. The client hands them over in order, and sends a `Heartbeat` 40 ms after a datagram that holds guaranteed messages when nothing else went out.
- The server checks the token of every datagram from the address of a player it admitted, on its network thread before any queue, and the sequence of every datagram it reads from a player, so a duplicate or a late one is dropped whatever its message. The client checks the token, then the sequence, of every datagram of the server.
- Each side sends a `Heartbeat` every 500 ms and measures the round trip from its echo, and the server sends each player `RoundTrips` after each of its `Heartbeat`s, as [Round trip](#round-trip) describes; the `Heartbeat` of the server also carries its tick during a game, as [Clock of the server](#clock-of-the-server) describes. The server keeps the seat of a silent player for 20 s in all, as [A session](#a-session) describes, and the client closes its session after 20 s without a datagram of the server.

- The client sends `LeaderboardRequest` from its leaderboard screen, and the server answers it.
- The supervisor checks the rules of a `NewGame` and opens its game with them. The creator of a game chooses its rules in the new game dialog of the server map, among the difficulties the master lists for that server (see [Client](/R-Type/client/#new-game-newgamemenu)); a client launched with `--game new` sends the default rules.
- The server sends `BossStatus` in the games whose difficulty names a boss, as [Boss status](#boss-status) describes, and the client shows the warning and the bar of the boss from it (see [Client](/R-Type/client/#boss-bosspresentation-bossbarat)).
- The server answers a request with a valid cookie with the `ConnectionAccepted` of the player and the content pack of the game, at most once per 250 ms per player once accepted. The supervisor serves its pack over HTTP, and the client plays with its own sheets, a pack it kept or a pack it downloads, as [Content pack](#content-pack) describes.
- The server limits the datagrams of each address and port, and of each player, on its network thread, as [A sender that sends too much](#a-sender-that-sends-too-much) says.
- The server relays the chat lines as [Chat](#chat) describes, and the client sends them so: one line at a time, again every 500 ms until it comes back, given up after 5 s.
- The supervisor sends `ExpulsionOrder` from its `kick` command, a game expels as [A peer disappears](#a-peer-disappears) describes, and the client ends its session at an `Expulsion`.
- The server shares the looks and gives the look items as [Ship looks](#ship-looks) describes, and the client sends its look from the waiting room and keeps the items won.
- The supervisor answers `ServerInformationRequest` as [Server information](#server-information) describes, and a game process does not. The server map of the client sends one to each server of this version the master lists, once per reading of the list (see [Client](/R-Type/client/#server-map-servermapscreen-iservercatalog-igamecatalog)).
- The master sends `MasterProbe`, and the server keeps its token and sends it back in its heartbeat, as [Probe of the master](#probe-of-the-master) describes.

What the programs do not do yet is listed at the end of [A peer disappears](#a-peer-disappears).
