1. Vue d'ensemble

Les grandes décisions qui structurent tout le reste : comment le code est découpé, qui tourne où, et pourquoi.

Architecture en couches (engine / game / network)

Le code est découpé en bibliothèques à dépendances à sens unique ; le client et le serveur sont les seuls endroits où elles se rencontrent.

Comment

Chaque dossier a son CMakeLists.txt qui déclare une cible. Les liens interdits sont vérifiés au configure par les fonctions CMake rtype_forbid_links et rtype_forbid_reachable_links (dans le CMakeLists.txt racine) : un lien illégal arrête CMake avant même la compilation.

Termes
Cible CMake
Une bibliothèque ou un exécutable que CMake construit (add_library, add_executable).
Dépendance à sens unique
A peut utiliser B, mais B ne connaît jamais A : le moteur ne sait rien du R-Type.
Configure
La première étape de CMake, qui lit les CMakeLists.txt et génère le build.
Logique

Le serveur ne doit pas embarquer une lib graphique, et la logique de jeu doit être identique côté client (prédiction) et serveur. En séparant rendu, réseau et règles, chaque partie se teste seule et le serveur reste « headless ».

Choix d'un ECS (Entity Component System)

Les objets du jeu sont des entités nues auxquelles on attache des composants (données) traités par des systèmes (comportement).

PR #15, #25, #32 · doc : architecture.md § Why an ECS

Où

src/engine/EntityRegistry/, src/engine/Components/, src/engine/Systems/ (détails en section 3).

Comment

Un ennemi, un vaisseau ou un missile n'est pas une classe : c'est un identifiant + une combinaison de composants (Position, Intent, CollisionBox, Health…). Les systèmes parcourent les entités qui ont les composants qui les intéressent.

Termes
Entité
Un simple identifiant (index + génération), sans données ni code.
Composant
Une struct de données pure attachée à une entité (ex. Position{x, y}).
Système
Un objet qui, à chaque tick, lit/modifie les composants d'un ensemble d'entités (ex. MovementSystem).
Archétype
Alternative (Unity DOTS, Bevy) : une table par combinaison de composants. Écartée ici.
Logique
  • Sépare données et comportement, comme le split engine/game.
  • Client et serveur partagent les composants ; seuls les systèmes diffèrent (rendu côté client, autorité côté serveur).
  • Un nouvel ennemi = une nouvelle combinaison de composants, pas une nouvelle classe dans une hiérarchie.
  • Ce n'est pas pour la vitesse : mesuré, une hiérarchie virtuelle est plus rapide (~1 ns vs ~28 ns par entité), mais à l'échelle du jeu ça ne compte pas.

Modèle réseau : serveur autoritaire, UDP, binaire

Le client n'envoie que les touches ; le serveur applique toutes les règles et renvoie l'état du monde.

PR #40, #162 · doc : architecture.md § Network model, technology-choices.md

Où

Règles : src/game/ exécutées par le serveur. Protocole : src/network/Protocol/. Spécification : docs/.../protocol.mdx.

Comment
ChoixGainCoût assumé
UDP plutôt que TCPUne perte ne bloque rien : l'état suivant remplace le perdu (pas de head-of-line blocking)Le protocole refait lui-même séquence, session, fiabilité des messages importants
Binaire plutôt que JSONPlayerInput = 31 octets vs 196 en JSON ; WorldState 113 vs 722 (6-7× moins)Illisible sans la spec, d'où une spec octet par octet, en big-endian
Serveur autoritaire plutôt que P2PUne seule vérité, pas de triche (le client ne déclare jamais une position)Latence d'un aller-retour, compensée par la prédiction
Termes
Autoritaire
Le serveur seul décide de l'état du jeu ; les clients ne font qu'afficher et prédire.
Head-of-line blocking
En TCP, un paquet perdu bloque tous les suivants jusqu'à sa retransmission.
Big-endian / ordre réseau
Octet de poids fort en premier, pour qu'un nombre se lise dans une capture comme il s'écrit.
Datagramme
Un paquet UDP indépendant, qui peut être perdu, dupliqué ou réordonné.
Logique

Dans un shoot'em up, une info vieille de 50 ms ne vaut plus rien : mieux vaut la remplacer que l'attendre. Le sujet impose UDP pour tout ce qui est « en jeu ». Le seul TCP du projet : HTTP vers le master et le téléchargement du content pack, hors du jeu lui-même.

Threads du serveur : réseau et simulation séparés

Deux threads ne partagent jamais l'état du jeu : ils se passent des datagrammes via des files bornées.

PR #55, #59 · doc : overview.md, concurrency.md

Où

src/server/ (application serveur), src/concurrency/BoundedQueue/.

Comment
  • Thread réseau : seul à toucher la socket ; reçoit, trie (vérifie token, séquence) et pousse dans des files entrantes ; envoie la file sortante.
  • Thread de simulation : 60 ticks/s ; vide les files, joue la partie, met les datagrammes à envoyer dans la file sortante.
  • Console d'administration : un thread qui lit l'entrée standard et passe chaque ligne au thread de simulation.
Termes
Tick
Un pas de simulation (1/60 s ≈ 16,7 ms).
File bornée
File de taille fixe : pleine, elle jette le plus vieux message (et le compte).
Logique

Comme un seul thread touche une partie, elle n'a besoin d'aucun verrou. La taille fixe des files empêche un client qui inonde le serveur de le faire grossir en mémoire.

Processus du serveur : superviseur, parties, master

r-type_server a trois rôles (--mode) : superviseur (défaut), une partie par processus, ou master.

PR #237, #248, #249 · doc : overview.md, server.md § roles

Où

src/server/ (rôles superviseur et game), src/master/ (rôle master). Un seul binaire, un main() qui choisit le rôle.

Comment
  1. Le joueur contacte le superviseur (port 4242, DEFAULT_SERVER_PORT).
  2. Le superviseur lance un processus --mode game (8 parties max, MAXIMUM_RUNNING_GAMES), sur un port choisi par le système.
  3. Le processus de jeu envoie un GameStatus chaque seconde au superviseur.
  4. Le superviseur redirige le joueur, qui rejoint directement la partie.
  5. Seul le superviseur parle au master (enregistrement, heartbeats).
Termes
Superviseur
Processus qui n'héberge aucune partie : il lance, surveille et route.
Master
Serveur central HTTP qui liste les serveurs de jeu (voir section 8).
Logique

Une partie qui crashe ne fait tomber que ses joueurs ; un plugin ou un réglage de partie ne tourne jamais dans le superviseur. Même idée que nginx (process master + workers). L'ancien mode « toutes les parties dans un processus » a été retiré.

Système de coordonnées logique (playfield)

Toute la logique utilise un repère de 1920 × 1080 unités, identique client et serveur, jamais des pixels.

PR #23, #37 · doc : architecture.md § Coordinate system

Où

src/game/Components/PlayfieldConstants.hpp (PLAYFIELD_WIDTH, PLAYFIELD_HEIGHT, STATUS_BAND_HEIGHT = 96, PLAY_AREA_HEIGHT = 984). Côté client : fitPlayfieldInWindow (src/client/Window/Display/).

Comment
  • Origine en haut à gauche, x vers la droite, y vers le bas.
  • Position = centre de l'entité ; vitesses en unités logiques par seconde ; CollisionBox centrée sur la position.
  • Le client est le seul à connaître les pixels : il choisit le plus grand rectangle 16:9 centré dans la fenêtre (bandes noires sinon).
Termes
Unité logique
Unité abstraite du jeu, convertie en pixels uniquement à l'affichage.
Letterboxing
Bandes noires qui comblent la fenêtre quand ses proportions diffèrent de 16:9.
Logique

Redimensionner la fenêtre ne change jamais une position ou une vitesse : le jeu se comporte pareil sur tous les écrans et le serveur n'a aucune notion d'affichage.

3. Moteur de jeu (engine)

La partie générique, dans src/engine/ (rtype_engine) : elle stocke les objets, fait avancer le temps, transporte les événements, lit la configuration. Elle ne sait rien de R-Type, de SFML ni des sockets. Les modules et plugins du moteur sont en section 10.

3.1 ECS : entités, composants, systèmes

Entités et recyclage par génération

Une entité n'est qu'une poignée {index, generation} ; les index des entités détruites sont réutilisés sans confusion possible.

PR #15 · doc : engine.md § Entities

Où

src/engine/Entity.hpp (struct Entity), src/engine/EntityRegistry/ (EntityRegistry).

Comment

EntityRegistry::create() prend un index dans une free list (liste des index libérés) ou en crée un nouveau. À la destruction, la génération de l'index est incrémentée : une poignée gardée après la destruction a l'ancienne génération, donc isAlive() renvoie faux et elle n'atteint jamais l'entité qui a pris sa place.

Termes
Handle (poignée)
Valeur qui désigne un objet sans le contenir.
Génération
Compteur par emplacement qui distingue les entités successives d'un même index.
Free list
Liste des index libérés, réutilisés en priorité pour garder les tableaux courts.
Stale handle
Poignée périmée (entité détruite) : elle ne lit plus rien.
Logique

Réutiliser les index garde les tableaux petits (sinon ils grandiraient toute la partie), et la génération évite le bug classique « je touche l'entité qui a remplacé celle que je visais ».

Composants et stockage en sparse set

Chaque type de composant a son tableau contigu ; ajout, lecture et suppression en temps constant.

PR #25 · doc : engine.md § Components, architecture.md § Components

Où

src/engine/Components/ : ComponentRegistry, ComponentStorage<T>, EntityIndexMap. Les composants du jeu : src/game/Components/ (Position, Intent, CollisionBox, EntityType, NetworkIdentity…).

Comment
  • add<T>, get<T> (pointeur ou nullptr), has<T>, remove<T>. Le stockage d'un type est créé au premier add : rien à enregistrer.
  • Un ComponentStorage<T> = un std::vector<T> sans trous + un EntityIndexMap (index d'entité → position dans le vecteur).
  • Suppression = on déplace le dernier élément dans le trou (swap removal).
  • destroy(entity) retire tous les composants puis l'entité ; add sur une entité morte lève DeadEntityException.
Termes
Sparse set
Deux tableaux : un « dense » (les données, compactes) et un « sparse » (index d'entité → position dans le dense).
Swap removal
Supprimer en échangeant avec le dernier élément, pour ne jamais laisser de trou.
Sparse array
Alternative écartée : vector<optional<T>> indexé par entité, qui gaspille de la mémoire.
Logique

Un compromis simple : trois tableaux par type, pas de déplacement d'entité entre tables (contrairement aux archétypes). Mesuré : ~28 ns par entité dans forEach, coût dominé par la recherche du stockage par hash, pas par le stockage lui-même — négligeable avec ~6 entités moyennes par partie.

Comment

3.2 Temps et boucle de jeu

Pas de temps fixe (FixedTimestep)

La simulation avance à 60 ticks par seconde, quelle que soit la vitesse de la machine ou du rendu.

Où

src/engine/Time/ : IClock, SystemClock, FixedTimestep, TimeConstants.hpp (SIMULATION_TICKS_PER_SECOND = 60, MAXIMUM_TICKS_PER_ADVANCE = 5). Boucle serveur : TickLoop (src/server/). Tests : tests/SimulatedClock.hpp.

Comment

  timers.advance(SIMULATION_TICK_DURATION);
  systems.run(components, SIMULATION_TICK_DURATION);
  events.dispatch();

Le reste du temps (moins d'un tick) est gardé pour l'appel suivant. Au-delà de 5 ticks de retard (~83 ms), l'excédent est abandonné (droppedTime() le signale).

Termes
Accumulateur
Technique de Glenn Fiedler (Fix Your Timestep!) : le temps réel s'accumule, la simulation le consomme par pas fixes.
Spiral of death
Être en retard fait simuler plus de pas, ce qui met encore plus en retard. La limite de 5 ticks la coupe.
IClock
Interface d'horloge : vraie horloge en production, horloge simulée dans les tests.
Logique

Un pas fixe rend la simulation reproductible : une collision ne dépend pas du nombre de FPS, et un test donne le même résultat à 30, 60 ou 144 FPS. Seul le serveur simule à pas fixe ; le client n'a pas de tick, il anime avec le temps réel de chaque frame.

Où

Horloge du serveur vue par le client (ServerClock)

Où

Comment
  • Chaque échantillon = tick du serveur + heure d'arrivée + aller-retour (RTT).
  • Estimation de l'instant du tick 0 = arrivée − RTT/2 − ticks écoulés.
  • Garde les 8 estimations les plus récentes et suit celle au plus petit RTT (filtre d'horloge NTP).

Logique

Indispensable à la prédiction et à l'interpolation : le client doit savoir « quel tick le serveur joue en ce moment ». Limite connue : si l'aller et le retour n'ont pas la même durée, l'estimation est décalée de la moitié de la différence, et rien ne peut le détecter.

3.3 Événements et collisions

Bus d'événements (EventBus)

Où

Comment

4.2 Concurrence

File bornée entre threads (BoundedQueue)

La seule manière dont deux threads se passent des messages ; pleine, elle jette le plus ancien.

Où

Comment
  • Tampon circulaire de capacité fixe, réservée une fois, protégé par un mutex.
  • push(message) : si plein, jette le plus vieux, l'ajoute à discardedCount() et renvoie true.

Contrainte C++20 sur un type de template, vérifiée à la compilation.

Logique

Le thread de jeu n'attend jamais le réseau. Jeter le plus ancien plutôt que bloquer l'écrivain : la dernière entrée d'un joueur vaut plus qu'une vieille, et un flood ne fait pas grossir la mémoire. Push + drain ≈ 20 ns.

Canal où le lecteur ne voit que la valeur la plus récente.

Valeur calculable par le serveur seul (hash à clé), qu'il n'a pas besoin de stocker. Même idée que les SYN cookies de TCP.
SipHash-2-4
Fonction de hachage à clé rapide pour messages courts ; implémentée par l'équipe et testée sur les vecteurs officiels.
Amplification
Attaque où un petit paquet forgé provoque une grosse réponse vers une victime. Ici, sans cookie valide, la réponse est toujours plus petite que la requête.
Usurpation d'adresse (spoofing)
Envoyer avec une fausse adresse source.
Logique

Une simple requête suffirait pour un jeu local, mais sur internet quatre adresses forgées rempliraient la partie. Avec le cookie, le serveur ne réserve rien avant que l'émetteur prouve qu'il possède son adresse (idée de QUIC, RFC 9000).

Session : jeton, séquence, heartbeats et absence

Chaque datagramme porte le jeton et un numéro de séquence ; un silence de 5 s marque le joueur absent, 20 s ferme sa session.

PR #93, #100, #105, #127, #145, #153 · doc : protocol.mdx § A session, server.md § Silent players

Où

Serveur : DatagramSorter (jeton, sur le thread réseau), GameSessions / ArrivalLedger (séquence, pertes) dans src/server/Sessions/, SessionDatagram (en-tête de chaque envoi). Client : ServerSession, RoundTripWatch. Constantes HEARTBEAT_INTERVAL 500 ms, SESSION_TIMEOUT 5 s, RECONNECTION_GRACE 15 s.

Comment
  • Le jeton est vérifié avant la séquence : un paquet forgé ne fait jamais avancer le compteur.
  • Séquence 16 bits : un datagramme qui n'est pas plus récent que le dernier accepté est jeté (comparaison RFC 1982, isNewerSequence()).
  • Le serveur mesure le taux de pertes de chaque joueur via les trous dans les séquences (par lots de 100).
  • Heartbeat toutes les 500 ms dans les deux sens. 5 s sans rien : joueur « absent », siège, jeton, vaisseau et score gardés (le vaisseau s'arrête). 20 s : session fermée, les autres reçoivent PlayerLeft (TimedOut).
  • Quitter : Disconnection envoyé 3 fois à 50 ms d'écart (fermeture immédiate).
Termes
Serial number arithmetic (RFC 1982)
Comparer des compteurs qui rebouclent : « plus récent » = en avance de 1 à 32767 modulo 65536.
Heartbeat
Message périodique qui prouve qu'on est vivant et sert à mesurer le ping.
Grâce de reconnexion
Délai pendant lequel la place d'un joueur silencieux est gardée.
Logique

En UDP, le dernier reçu n'est pas forcément le plus récent : sans séquence, un vieux paquet en retard annulerait un plus récent. Garder la place d'un joueur silencieux couvre une micro-coupure réseau.

Limitation de débit et bannissements temporaires

Chaque émetteur a un budget de datagrammes ; qui le dépasse trop souvent est banni 10 s.

PR #82, #204, #209 · doc : network.md § Rate limit, server.md § Flood protection

Où

src/network/Handshake/RateLimit/ (spendAllowance, RequestAllowances, RateLimitConstants.hpp). Appliqué par DatagramSorter ; rapport des rejets : RejectionLedger.

Comment
  • Algorithme GCRA : on retient quand le prochain datagramme est « dû » ; un silence redonne au plus une rafale.
  • Requêtes de connexion : rafale de 11, puis 1 / 250 ms ; 20 rejets en 1 s → ban 10 s. Table fixe 256 × 4 emplacements (~104 Kio), ligne choisie par SipHash à clé (impossible de viser la ligne d'un autre).
  • Joueur en session : rafale 60, 120 datagrammes/s (2× le rythme normal).
  • Les rejets sont comptés par cause et par émetteur et résumés dans le journal.
Termes
GCRA
Generic Cell Rate Algorithm (ITU-T I.371), équivalent d'un « token bucket » avec 4 champs par émetteur.
Burst (rafale)
Nombre de paquets acceptés d'un coup après un silence.
DoS
Déni de service : saturer un serveur pour le rendre indisponible.
Logique

Une fenêtre « par seconde » laisserait passer le double à la frontière de deux fenêtres ; une table qui refuse les nouveaux une fois pleine bloquerait tous les vrais joueurs (défaut d'ioquake3). Ici la mémoire ne grandit jamais, quoi que fasse l'attaquant.

5.4 Fiabilité sur UDP

Messages garantis et ordonnés

Les messages qui changent l'écran une seule fois sont renvoyés jusqu'à acquittement et traités dans l'ordre.

PR #183, #230 · doc : protocol.mdx § Ordered messages, network.md § Guaranteed messages

Où

src/network/Reliability/ : ReceivedSequences, UnacknowledgedMessages, OrderedReceiver, GuaranteedDelivery.hpp. Serveur : MessageDelivery ; client : OrderedInbox.

Comment
  • Concernés : EntityDestroyed, EnemyAction, GameEvent, PlayerLeft, PlayerChatLine, BossStatus, PlayerLooks, LookItemWon (+ missiles du joueur).
  • Chacun est emballé dans un OrderedMessage numéroté (canal ordonné par joueur).
  • Chaque datagramme acquitte les 33 derniers reçus (en-tête). Non acquitté → renvoyé toutes les 100 ms, groupé avec les autres dus.
  • Abandonné après 1 s ou 256 numéros ; firstKept dit au récepteur d'arrêter d'attendre.
  • Le client envoie un heartbeat 40 ms après un message garanti s'il n'a rien d'autre à envoyer (porter l'acquittement).
Termes
ACK
Acquittement : « j'ai bien reçu le datagramme n ».
Bitfield d'acquittement
32 bits qui acquittent d'un coup les 32 datagrammes précédents (technique de Glenn Fiedler).
Enveloppe
Message qui en transporte un autre (innerType + payload).
Logique

Les états sont répétés 20×/s et se corrigent seuls ; une explosion ou un départ, non. L'ordre évite qu'un joueur meure à l'écran avant le tir qui l'a tué. Abandonner après 1 s garde l'écran à jour plutôt que rejouer des sons périmés. Avec 20 % de pertes, environ 1 message sur 2 millions est perdu.

Entrées répétées jusqu'à confirmation

Chaque PlayerInput répète les entrées que le serveur n'a pas encore confirmées.

Où

Client : PlayerInputPacer, IPlayerInputLink (src/client/Input/Commands/). Serveur : InputKeeper par partie.

Comment
  • Entrée = inputNumber (croissant), actions (5 bits : haut, bas, gauche, droite, tir), jusqu'à 15 entrées précédentes, shownTick.
  • Envoyée 60×/s (une par tick avec la prédiction), même sans touche.
  • Le serveur garde le plus grand numéro vu et prend, du plus vieux au plus récent, chaque entrée plus récente : une entrée perdue est récupérée dans le message suivant, une fois, dans l'ordre.

Redondance
Renvoyer volontairement les mêmes données pour survivre aux pertes sans retransmission.
Logique

Pas besoin de renvoi sur timer : une entrée perdue est rattrapée 17 ms plus tard. Indispensable pour que la prédiction du client et le serveur appliquent exactement les mêmes entrées.

Logique

Une entité immobile ne coûte rien. Ne jamais différencier contre un état non acquitté garantit que le client peut toujours reconstruire (technique de Quake 3 / Glenn Fiedler).

5.6 Masquer la latence

Prédiction du vaisseau et réconciliation

Le client bouge son vaisseau immédiatement avec le même code que le serveur, puis corrige d'après ce que le serveur confirme.

PR #170, #206, #266 · doc : client.md § Own ship prediction

Où

src/client/Prediction/OwnShip/ (OwnShipPredictor, ShipPrediction) ; code de mouvement partagé : shipAfter (src/game/ShipControl/). Toujours active : ce n'est pas un réglage du joueur.

Comment
  • Le client compte le temps en ticks entiers comme le serveur, envoie une entrée numérotée par tick et calcule la position prédite après chacune.
  • Il garde chaque entrée non confirmée avec la position prédite.
  • À chaque état : lit acknowledgedInput et la position serveur ; jette les entrées confirmées ; si l'écart dépasse RECONCILIATION_TOLERANCE (16 unités), repart de la position serveur et rejoue les entrées suivantes.
  • Après une correction, le vaisseau glisse vers la bonne position au lieu de sauter.
Termes
Client-side prediction
Appliquer localement l'effet d'une entrée sans attendre le serveur.
Server reconciliation
Repartir de l'état serveur confirmé et rejouer les entrées pas encore confirmées (Gabriel Gambetta).
Déterminisme
Mêmes entrées → même résultat : d'où l'usage du même shipAfter des deux côtés.
Logique

Sans prédiction, une touche n'agit qu'après un aller-retour + un intervalle d'état. Le sujet impose l'autorité du serveur sur les monstres, pas l'interdiction de prédire son propre vaisseau.

Interpolation des autres entités

  • Double appui d'une direction en moins de 13 entrées (217 ms) : roulade (haut/bas) ou dash/backstep (gauche/droite), avec temps de recharge de 500 ms. Compté en numéros d'entrée, donc indépendant du réseau.

7.1 Architecture d'exécution

Superviseur et processus de jeu

Le superviseur n'héberge aucune partie : il en lance jusqu'à 8, place les joueurs et les redirige.

Où

Comment
  • Le superviseur répond aux requêtes de connexion (cookie), choisit une partie avec GameRegistry::placeFor() : rediriger (ConnectionRedirect + port), attendre, ouvrir un nouveau processus, ou refuser (ServerFull, GameFull…).

  • Chaque partie envoie un GameStatus chaque seconde (état, pseudos, mesures) ; le superviseur l'acquitte.
  • SeatReservations : un siège est réservé 3 s pour chaque joueur redirigé, pour qu'une rafale de 5 joueurs ouvre bien une 2e partie.

Logique

Lien avec le master

Le superviseur s'enregistre auprès du master, lui envoie ses parties et ses mesures, puis les résultats vanilla.

PR #210, #217, #218, #245, #276, #292, #296 · doc : server.md § Link with the master

Où

Comment
  • Avec master-url + master-key : enregistrement (nom, port, versions, capacité, secret de sonde), puis heartbeat à chaque changement (≥ 1 s d'écart) et périodiquement.
  • Après chaque heartbeat accepté : jusqu'à 16 résultats vanilla envoyés (PUT /api/servers/me/results/{gameId}, idempotent).
  • Le master sonde le port UDP (MasterProbe) ; le jeton reçu revient dans le heartbeat suivant (prouve que le port est joignable).
  • Master injoignable : logué une fois, puis nouvel essai après une attente tirée au hasard entre 0 et un plafond ; le plafond part de 5 s et double à chaque échec, jusqu'à 60 s (MAXIMUM_REGISTRATION_RETRY), et revient à 5 s dès qu'un enregistrement passe. Le jeu n'attend jamais.
  • master-url accepte http:// et https:// ; en HTTPS, MasterClient vérifie le certificat avec les autorités du système.
Termes
Idempotent
Envoyer deux fois donne le même résultat : un résultat renvoyé ne compte pas double.

Attendre de plus en plus longtemps entre deux essais ratés, d'une durée tirée au hasard sous un plafond qui double (méthode décrite par Marc Brooker sur le blog AWS).
Logique

Un seul enregistrement pour toutes les parties du superviseur ; sans master, le serveur fonctionne seul. Le hasard évite que tous les serveurs qui ont perdu le même master le rappellent dans la même seconde quand il revient. Prix : un serveur peut mettre jusqu'à 60 s à réapparaître dans la liste.

Le master : un mode du binaire serveur, en HTTP

Une API REST JSON sur HTTP/TCP, construite avec les mêmes modules, config et journal que le serveur.

Où

Comment
  • Modules dans l'ordre : logger, storage (SQLite r-type_master.db), probe, http, servers, leaderboard. Pas de boucle de ticks : les threads HTTP répondent.

  • Routes RESTful : ressources au pluriel, méthode = action, l'appelant désigné par sa clé (/api/servers/me), jamais par un id dans le chemin.

RFC 9457
Format standard JSON des erreurs HTTP (« problem details »).

Logique

HTTP plutôt qu'un protocole maison : le navigateur (site web) ne parle que HTTP, curl suffit pour tester, un reverse proxy ajoute HTTPS sans code (c'est ce que fait Caddy en production). Le sujet autorise TCP pour ce qui n'est pas « en jeu ». Un mode du binaire serveur plutôt qu'un 3e binaire : le sujet ne liste que deux binaires (comme DDNet qui enregistre ses serveurs en HTTP).

Content pack : distribuer le contenu aux clients

Le superviseur sert ses fiches et sprites en un fichier ; un client qui ne l'a pas le télécharge en rejoignant.
